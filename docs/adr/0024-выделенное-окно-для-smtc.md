# ADR-0024: Выделенное окно для Windows SMTC

**Статус:** Принято (2026-10-24)  
**Дата:** 2026-10-24  
**Участники решения:** ModernByte Architecture, Юрий Анатольевич  

## Контекст

ADR-0006 выбрал playwire для системных медиа-контролов, включая System Media
Transport Controls (SMTC) на Windows. Фактическая реализация `MediaControls::new`
(`src/media/mod.rs:64-78`) собирает `PlayerConfig` без `hwnd`, поэтому на Windows
инициализация playwire завершается `Error::Config`
(`playwire-2.0.0/src/platform/windows.rs:92-94`). `launch()` перехватывает ошибку и
продолжает без медиа-контролов (`src/main.rs:163-169`); MPRIS на Linux работает.

Ограничения, задающие решение:

1. **SMTC привязан к окну.** `ISystemMediaTransportControlsInterop::GetForWindow`
   принимает `appWindow`; документация Microsoft требует, чтобы это было
   «top-level window that belongs to the calling process».
2. **Окно eframe не переживает скрытие.** ADR-0018: скрытие окна — закрытие
   root-вьюпорта и остановка UI-цикла; сессия, эфир, IPC и MPRIS продолжают жить.
   Привязка SMTC к HWND eframe потеряет контролы при скрытии, а перепривязка при
   каждом показе даст разрывы в системном виджете и риск повторной регистрации.
3. **У playwire нет перепривязки.** HWND передаётся только при создании
   `MediaControls`; сменить окно у существующего экземпляра нельзя.
4. **Медиа-контролы создаются до окна и живут в Session** (`src/main.rs:146-174`),
   то есть их время жизни — весь процесс, а не один прогон вьюпорта.

## Решение

1. На Windows `src/media/` создаёт **скрытое top-level окно** (не message-only),
   которое живёт от создания медиа-контролов до завершения процесса. Linux и macOS
   это решение не затрагивает.
2. Окно создаётся на **выделенном потоке** с собственным циклом сообщений
   (`GetMessageW` / `TranslateMessage` / `DispatchMessageW`). Поток сообщает HWND
   через канал; вызывающий поток ждёт готовности с таймаутом.
3. Параметры окна: стиль `WS_POPUP`, расширенные стили
   `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`, без `WS_VISIBLE`, нулевой размер, без
   родителя (top-level), оконная процедура — `DefWindowProcW`. Окно не появляется
   в панели задач, Alt-Tab и на экране. Имя класса и заголовок — `OrbitFM …`.
4. `HostWindow` отдаёт HWND, который передаётся в `PlayerConfig::hwnd`. Дескриптор
   хранится в `MediaControls` и переживает все показы и скрытия окна eframe.
   Сигнатура `MediaControls::new(wake)` не меняется — это платформенная деталь
   медиа-модуля, а не публичный контракт.
5. Завершение: `Drop` отправляет окну `WM_APP + 1`; поток владельца уничтожает
   окно, вызывает `PostQuitMessage` и завершается, после чего `Drop` делает
   `join`. Порядок полей структуры гарантирует, что `PlatformControls`
   освобождается раньше окна.
6. Зависимость: `windows = "0.62"` только для `cfg(windows)` с фичами
   `Win32_Foundation`, `Win32_UI_WindowsAndMessaging`,
   `Win32_System_LibraryLoader` (нужна для `GetModuleHandleW`) и
   `Win32_Graphics_Gdi` (без неё windows-rs не компилирует `WNDCLASSW` —
   его поле `hbrBackground` ссылается на `HBRUSH`). Версия `0.62.2` уже в дереве
   через playwire 2.0, новых crate-версий не появляется.
7. Ошибка создания окна не фатальна: `MediaControls::new` возвращает ошибку,
   `launch()` логирует предупреждение и работает без системных медиа-контролов —
   как сейчас.
8. AppUserModelID и имя приложения в flyout вне рамок этого ADR: MSI создаёт
   ярлык без явного `System.AppUserModel.ID`; поведение проверяется на Windows,
   при необходимости — отдельное решение по упаковке.

**Message-only окно отклонено:** документация `GetForWindow` прямо требует
top-level окно, а message-only окно таковым не является (его родитель —
`HWND_MESSAGE`).

## Последствия

**Положительные:**
- SMTC инициализируется и не зависит от жизненного цикла вьюпорта: управление
  эфиром сохраняется при скрытом окне, как требует ADR-0018.
- Единый экземпляр `MediaControls` на процесс — без дублирования регистрации и
  разрывов при show/hide.
- Публичный контракт медиа-модуля не меняется, Windows-код изолирован `cfg`.

**Отрицательные / Риски:**
- В текущем окружении (Linux) возможна только компиляционная проверка; рантайм
  SMTC нужно проверить вручную на Windows: play/pause/stop/next/previous, колесо
  громкости, скрытие и повторный показ окна, отсутствие окна в Alt-Tab.
- Дополнительный поток и прямая зависимость от Win32 API.
- `join` при завершении может задержать выход, если цикл сообщений завис; риск
  считается низким, сценарий проверяется на Windows.

## Альтернативы

| Вариант | Причина отклонения |
|---------|--------------------|
| HWND окна eframe с перепривязкой при каждом показе | Противоречит ADR-0018: при скрытом окне SMTC теряет регистрацию, системные контролы пропадают |
| Message-only окно (`HWND_MESSAGE`) | Документация `GetForWindow` требует top-level окно |
| `GetConsoleWindow` / `GetActiveWindow` | Ненадёжно: GUI-подсистема без консоли, чужое активное окно, нет гарантии владения |
| Переход на souvlaki | Тоже требует HWND и не решает вопрос времени жизни; ADR-0006 оставляет его лишь запасным вариантом |
| Видимое служебное окно | Лишний элемент UI, не нужен для SMTC |
