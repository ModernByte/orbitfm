# ADR-0011: Поставка Linux и упаковка

**Статус:** Принято, редакция 2  
**Дата:** 2026-10-22 · ред. 2 — 2026-11-19  
**Участники решения:** ModernByte Architecture, Юрий Анатольевич  

## Контекст

Этап 6 требует упаковки AppImage / MSI / DMG. Фактическое окружение
разработки — Linux x86_64 (CachyOS, Wayland, mpv 0.41 / FFmpeg 12.1). Для Windows и
macOS отсутствуют нативные раннеры, SDK и сборки libmpv; кросс-проверка `cargo check`
упирается в C-зависимости (`aws-lc-sys` требует mingw-компилятор). Кроме того, в коде
пока нет Windows named pipe и привязки SMTC к HWND, а macOS Now Playing требует
запущенного `NSApplication` в момент регистрации. MSI и DMG нельзя собрать и проверить
без Windows/macOS.

При этом метаданные рабочего стола (desktop entry, иконка, AppStream) нужны для любого
формата поставки и не зависят от платформенных бэкендов.

Редакция 2 (2026-11-19) фиксирует сужение канала поставки: **Flatpak удалён из проекта
полностью** — манифест, вендинг Cargo-исходников, скрипт сборки, шаги CI и упоминания в
документации и вики. Причина и границы отказа — в уточнении 2026-11-19 ниже.

## Решение

1. Единый источник метаданных рабочего стола — `packaging/linux/`:
   `org.modernbyte.OrbitFM.desktop`, `org.modernbyte.OrbitFM.metainfo.xml` и
   масштабируемая иконка `org.modernbyte.OrbitFM.svg`.
2. Основной проверяемый артефакт Linux — **AppImage**, который собирает
   `packaging/linux/build-appimage.sh`: release-сборка, `linuxdeploy` (бандлинг
   динамических библиотек, включая libmpv и FFmpeg) и `appimagetool`.
   Результат — `target/appimage/OrbitFM-<version>-x86_64.AppImage`.
3. Инструменты AppImage не входят в репозиторий: скрипт использует `LINUXDEPLOY` и
   `APPIMAGETOOL` из окружения либо скачивает их в `target/appimage-tools` и
   сверяет с зафиксированным SHA-256. `appimagetool` берётся из неизменяемого
   релизного тега `1.9.1`: канал `continuous` пересобирается под тем же URL и
   2026-11-06 снял сборку релиза (см. уточнение ниже). Для сред без FUSE
   применяется `APPIMAGE_EXTRACT_AND_RUN=1`.
4. CI проверяет метаданные (`desktop-file-validate`, `appstreamcli validate`,
   `bash -n`, XML/plist); сборку AppImage выполняет release-workflow.
5. **Отложено до появления платформенных бэкендов (MSI/DMG разблокированы
   2026-10-23, см. уточнение ниже):**
   - Windows (SMTC) — привязка playwire к HWND;
   - macOS (Now Playing) — рантайм-проверка Now Playing.

   Критерий возврата: зелёная сборка и ручная проверка медиа-интеграции на
   соответствующей ОС. До этого пункты ROADMAP остаются незакрытыми с пометкой
   «заблокировано».
6. **MSI и DMG в CI (2026-10-23).** Нативные установщики собираются отдельными
   джобами и публикуются артефактами `actions/upload-artifact`; во внешние
   каналы не выкладываются:
   - Windows: MSYS2 UCRT64 `mingw-w64-ucrt-x86_64-mpv` (libmpv 0.41.0); импорт
     `mpv.lib` генерируется из `libmpv-2.dll` через `dumpbin` и `lib.exe`;
     MSVC release-сборка; транзитивные DLL собираются по таблицам импорта через
     `objdump`; MSI собирает WiX 5 (последняя версия без OSMF EULA, которую
     требуют v6+) для per-user установки в `%LOCALAPPDATA%\Programs\OrbitFM`
     с ярлыком в меню «Пуск»; CI выполняет тихую установку и удаление MSI.
   - macOS: `.app` с `Info.plist`, иконкой `.icns` (из общего SVG через
     `rsvg-convert`/`iconutil`), зависимости бандлятся `dylibbundler`, подпись
     ad-hoc; DMG (UDZO) содержит приложение и ссылку на `/Applications`;
     CI монтирует DMG и проверяет подпись и отсутствие ссылок на Homebrew.
   - Артефакты не подписаны сертификатами и не нотаризованы: MSI не имеет
     Authenticode, DMG — Developer ID и notarization. Это осознанное ограничение
     до появления сертификатов у владельца.
7. **Один канал на Linux (ред. 2).** Пользователь получает AppImage (`install.sh`
   одной командой либо `install-appimage.sh` вручную) либо дистрибутивную сборку.
   Второго, песочного канала нет — см. уточнение 2026-11-19.

## Альтернативы

| Вариант | Причина отклонения |
|---------|--------------------|
| Только tar.gz | Не соответствует ROADMAP и не даёт интеграции с рабочим столом |
| Flatpak | Отклонён 2026-11-19 (ред. 2): в песочнице недоступны виджет Noctalia и внешний CLI, а второй канал требовал манифеста, вендинга Cargo-исходников и собственного чекера — цена без пользовательского сценария. Подробности — в уточнении 2026-11-19 |
| Статическая сборка musl | libmpv, wgpu и Wayland/EGL делают её непрактичной |
| Пакеты дистрибутивов (deb/rpm/AUR) | Отдельная инфраструктура и поддержка; возможна позже |

## Последствия

**Положительные:**

- Есть проверяемый переносимый артефакт для Linux
- Метаданные рабочего стола переиспользуются дистрибутивными пакетами
- Один канал поставки вместо двух: меньше поверхностей, которые надо держать
  согласованными (манифест, вендинг, чекер, отдельная документация)
- Блокеры кроссплатформенности зафиксированы явно, а не замаскированы «зелёным» чекбоксом

**Отрицательные / Риски:**

- AppImage наследует ограничения хостового libmpv/FFmpeg и драйверов; проверен только
  на x86_64 Linux
- Пользователь, которому нужна песочница, остаётся с дистрибутивным пакетом или
  самостоятельной сборкой: такого канала проект не поддерживает
- `linuxdeploy` не закреплён по неизменяемому тегу (только по дайджесту); риск
  расхождения канала `continuous` снимается дайджест-гейтом, а не тегом
- MSI/DMG собираются без подписи и нотаризации; для релиза потребуются сертификаты
  владельца

## Уточнение (2026-10-23): нативные CI-джобы

- macOS (`macos-latest`): libmpv из Homebrew, `fmt`, `clippy`, тесты и release-сборка.
- Windows (`windows-latest`): `fmt` и `clippy`; проверяется компиляция. Реализован
  named pipe IPC (`src/ipc/pipe.rs`).
- MSI и DMG на этом шаге ещё не собирались; ниже добавлены отдельные джобы упаковки.

## Уточнение (2026-10-23): MSI и DMG

- Джоба `msi` (`windows-latest`): MSYS2 UCRT64 с `mingw-w64-ucrt-x86_64-mpv`
  (libmpv 0.41.0). `prepare-libmpv.ps1` извлекает экспорты через `dumpbin` и
  собирает `mpv.lib` через `lib.exe`; `RUSTFLAGS=-L native=...` указывает путь
  MSVC-линкеру. `stage-app.sh` обходит DLL-замыкание через `objdump`, после чего
  добавляются runtime DLL MSVC. WiX 5 (v5.0.2) собирает per-user MSI
  (`%LOCALAPPDATA%\Programs\OrbitFM`, ярлык в меню «Пуск»); CI проверяет тихую
  установку и удаление.
- Джоба `dmg` (`macos-latest`): `build-dmg.sh` собирает `.app`, генерирует
  `.icns` из общего SVG, бандлит зависимости через `dylibbundler`, подписывает
  ad-hoc и создаёт UDZO DMG со ссылкой на `/Applications`; CI монтирует образ,
  проверяет подпись и отсутствие ссылок на Homebrew.
- Оба артефакта публикуются через `actions/upload-artifact` и не выкладываются
  во внешние каналы. MSI не подписан Authenticode, DMG не подписан Developer ID
  и не нотаризован — это ограничение до появления сертификатов у владельца.

## Уточнение (2026-10-29): LGPL-2.1 и контур поставки

- **LGPL-2.1 у обёрток libmpv.** `libmpv2` и `libmpv2-sys` — единственные
  copyleft-пакеты графа (замер по 558 пакетам `Cargo.lock`). Обязательства
  покрываются динамической линковкой, и ни один артефакт не исключает замену
  библиотеки: замеры локальной сборки показывают `NEEDED libmpv.so.2` в
  бинарнике и `AppDir/usr/lib/libmpv.so.2` отдельным файлом (174 `.so` всего),
  MSI кладёт `libmpv-2.dll` в каталог приложения, DMG несёт `.dylib` в
  `Contents/Frameworks` (бандлинг через `dylibbundler`). Статическая линковка
  libmpv в этих форматах запрещена как класс решений: она превратила бы
  LGPL-артефакт в неисправляемый пользователем бинарник. Релизный workflow
  проверяет это отдельным шагом (`Verify libmpv stays replaceable (LGPL)`),
  потому что «запрещено как класс» без гейта — это пожелание, а не ограничение.
  `deny.toml` держит `LGPL-2.1` в `allow` ровно по этому обоснованию — сам по
  себе copyleft в список не попадает.
- **Контур поставки.** `packaging/cargo-deny-check.sh` — единая точка: сначала
  требует, чтобы каждая прощённая запись `[advisories] ignore` имела
  `# revisit: ГГГГ-ММ-ДД` и чтобы ни одна дата пересмотра не истекла, затем
  ставит `cargo-deny` строго пиннованной версии с проверкой SHA256 и гоняет
  `cargo deny check` по графу целиком (без `-t/--target`: платформенные
  зависимости macOS и Windows тоже входят в артефакты). Job `supply-chain` в CI
  и тот же шаг гейтом в релизном workflow — потому что пуш тега CI не
  триггерит, а артефакты не должны уезжать с непроверенным графом.
  Чекер вендинга Flatpak (`check-flatpak-sources.py`) в этом контуре был
  отдельной проверкой до редакции 2 и удалён вместе с каналом (уточнение
  2026-11-19).
- **Что здесь не решено.** Подписи артефактов (Authenticode, Developer ID,
  notarization) и detached-сигнатуры к `SHA256SUMS` — по-прежнему зона
  ответственности владельца: сертификат не заведён, поэтому релизы подписываются
  только ad-hoc, а `SHA256SUMS` содержит дайджесты, а не сигнатуры.

## Уточнение (2026-11-01): интеграция AppImage без root

`packaging/linux/install-appimage.sh` публикуется рядом с AppImage как
`install-appimage.sh` и ставит скачанный образ в меню приложений:

- копирует AppImage в `${XDG_BIN_HOME:-$HOME/.local/bin}/orbitfm` и делает
  копию исполняемой, поэтому пользователю не нужен `chmod +x`;
- распаковывает образ через `--appimage-extract` во временный каталог и
  устанавливает desktop entry, иконки hicolor и metainfo в `XDG_DATA_HOME`;
- правит только строки `Exec=`/`TryExec=` по точному префиксу ключа (без
  регулярных выражений), сохраняя аргументы (`mode focus`) и остальные строки;
  путь с пробелами экранируется по Desktop Entry Specification;
- пишет список установленных файлов в
  `${XDG_STATE_HOME:-$HOME/.local/state}/orbitfm/appimage-install.list`;
  `--uninstall` удаляет только пути внутри сохранённых `BIN_HOME`/`DATA_HOME`;
- обновляет `update-desktop-database` и `gtk-update-icon-cache`, если они есть,
  и предупреждает, если каталог установки отсутствует в `PATH`.

Ограничения: установленный файл остаётся AppImage, поэтому для запуска нужен
FUSE либо `APPIMAGE_EXTRACT_AND_RUN=1`; обновление — повторный запуск скрипта с
новым образом; AppImageLauncher не требуется, но и не конфликтует с ним.

## Уточнение (2026-11-01): подписи — состояние и поэтапный план

Сейчас:

- MSI не подписан Authenticode и не имеет метки времени;
- DMG подписан только ad-hoc (`codesign --sign -`), без Developer ID,
  hardened runtime и notarization;
- Linux-артефакты не имеют detached-подписи: `SHA256SUMS` лежит на той же
  странице релиза и защищает от повреждения, но не от подмены.

План (не реализован: нужны сертификаты и секреты владельца; ключи не попадают в
репозиторий):

1. **Linux — detached-подпись.** Minisign или OpenPGP-подпись над `SHA256SUMS`
   (и, при желании, над каждым артефактом), публичный ключ в README. Подпись
   ставится после сборки всех артефактов и после генерации контрольных сумм,
   иначе подписывается устаревший дайджест. Проверка — одной командой,
   сертификат не нужен. Это первый шаг: он не зависит от платформ и закрывает
   целостность канала.
2. **Windows — Authenticode.** OV- или EV-сертификат, ключ в аппаратном токене
   или облачном HSM (Azure Trusted Signing, DigiCert KeyLocker и аналоги).
   Подписываются исполняемые файлы до сборки MSI и сам MSI, ставится RFC 3161
   timestamp; CI проверяет `signtool verify /pa /all`. EV даёт немедленную
   репутацию SmartScreen, OV набирает её постепенно; до этого SmartScreen
   предупреждает, как описано в README.
3. **macOS — Developer ID и notarization.** Сертификат Developer ID Application
   (платная программа Apple Developer), hardened runtime, подпись
   `codesign --options runtime`, отправка `notarytool submit --wait`, затем
   `stapler staple` и проверка `spctl --assess --type execute`. Секреты —
   Apple ID с app-specific password или App Store Connect API key в CI.
4. **Порядок.** Сначала Linux-подпись, затем Windows и macOS, потому что
   последние два требуют покупки сертификатов и настройки CI-секретов. До
   появления ключей релизы остаются не подписанными коммерческими
   сертификатами, и документация обязана это говорить прямо; самоподписанные
   сертификаты не используются — Gatekeeper и SmartScreen им не доверяют.

После включения подписей `SHA256SUMS` генерируется заново после каждого шага
подписи; порядок «сборка → подпись → дайджесты → detached-подпись дайджестов»
фиксируется в release-workflow.

## Уточнение (2026-11-06): DMG для двух арок и чем обеспечивается бандл

Описанное выше (уточнение от 2026-10-23) про DMG устарело в трёх деталях, и они важны,
потому что именно вокруг них собраны гейты:

- `.icns` генерируется не из SVG, а из закоммиченного PNG
  (`packaging/macos/OrbitFM-1024.png`, `sips` + `iconutil`): под Intel у Homebrew нет
  бутылок, и `rsvg` пришлось бы собирать из исходников.
- Джоба `dmg` — матрица из двух арок (`arm64` на `macos-latest`, `x86_64` на
  `macos-15-intel`), а не одна `macos-latest`; публикуются два DMG, universal2 не
  собирается, а причина отказа зафиксирована в `docs/adr/0052-матрица-поддержки-macos.md` §4.
- `libmpv` берётся не из `brew install`, а из закреплённых бутылок Homebrew под macOS 13
  (`packaging/macos/fetch-libmpv.py`): `brew` на `macos-latest` в 2026 году положил бы в
  бандл библиотеки под macOS 26, и DMG перестал бы запускаться на 13–15.

Гейты бандла, кроме проверки подписи и отсутствия ссылок на Homebrew:
`packaging/macos/check-app-arch.sh` (каждый Mach-O бандла обязан иметь ровно объявленную
`--arch` по `lipo -archs` — ловит fat-бинарник, Rosetta-подмену и чужеродный dylib),
`packaging/macos/audit-app-dylibs.sh` (load-команды), `packaging/macos/check-min-os.py`
(`LC_BUILD_VERSION` каждого Mach-O против предела из `Info.plist` + срез арки),
`packaging/macos/smoke-launch.sh` (реальный запуск `--version`: аудит путей не видит
случай «библиотека на месте, символа нет», что и убило `0.20.0-rc.5`) и четыре негативных
fixture в `ci.yml` — на аудит, на недостающий символ, на арку и на поле
`LSMinimumSystemVersion` ниже фактического требования; каждый обязан упасть и печатает в
лог маркер, чтобы зелёный шаг нельзя было спутать с пропущенным. Полное решение по
поддержке, архитектурам и минимальной ОС —
`docs/adr/0052-матрица-поддержки-macos.md`; подпись при этом остаётся
ad-hoc (п. 3–4 плана подписей выше не реализован).

## Уточнение (2026-11-06): пиннинг appimagetool на релизный тег

Сборка релиза `0.21.0-rc.1` упала на job `linux`: скачанный `appimagetool` не совпал с
зафиксированным SHA-256. Причина — не подмена и не ошибка пиннинга, а сам канал:
`releases/download/continuous/` перезаписывается новым ассетом под неизменным URL.
На момент падения там лежал build 370 (git `11d54c9`) со сборкой `2026-11-06 00:47 UTC`,
то есть полутора часами раньше job; за неделю до этого тот же канал уже потребовал
правки AppDir (PNG в корне, `2026-10-31`). Дайджест-гейт отработал как задумано —
сборка не выпустилась молча, а остановилась, — но цена такой остановки — перенос релиза.

**Решение.** `appimagetool` скачивается из неизменяемого релизного тега `1.9.1`
(ассет build 296, git `8c8c91f`, не менялся с `2025-12-04`), дайджест
`ed4ce84f...3cb384eb0` закреплён вместе с URL. Требование к `--no-appstream` проверено на
самом пиннутом ассете; собранный им AppImage содержит `.DirIcon` и отвечает
`orbitfm 0.21.0-rc.1`.

`linuxdeploy` остаётся на `continuous` с дайджестом. Теги у него есть, но это
датированные альфы (`1-alpha-20251107-1` и старше) — свежее закрепленной сборки они не
лежат, поэтому перевод бандлера на них был бы сменой содержимого AppImage, а не
успокаивающей правкой URL; в правке, разблокировавшей релиз, такого решения нет. Риск
расхождения по каналу `continuous` для него сохраняется, и ловится он тем же
дайджест-гейтом.

Обновление пина — правка в той же правке, что и проверка нового AppImage: тег меняется
осознанно, а не «потому что upstream что-то пересобрал».

## Уточнение (2026-11-16): установка одной командой

Причина — порог входа: скачать AppImage, сделать `chmod +x` и отдельно запустить
`install-appimage.sh` — три шага, которые пользователь проходит до первого звука.

**Решение.** `install.sh` в корне репозитория — тонкая обёртка над уже принятой
интеграцией, а не второй установщик:

- находит последний релиз через GitHub API (`--release <версия>` фиксирует тег,
  `ORBITFM_RELEASE` делает то же для скриптов);
- скачивает AppImage, `install-appimage.sh` и `SHA256SUMS`; обе суммы сверяются до
  запуска, поэтому неподписанный канал остаётся таким же, как при ручной установке;
- сохраняет помощник в `${XDG_STATE_HOME:-$HOME/.local/state}/orbitfm/install-appimage.sh`
  и запускает его: установка и раскладка файлов остаются в одном месте;
- `--uninstall` работает без сети сохранённым помощником той версии, `--dry-run`
  только скачивает и проверяет, `--help` печатает справку;
- поддерживается только Linux x86_64: другой архитектуры в релизе нет, macOS и
  Windows остаются на DMG и MSI, и обёртка говорит об этом явно.

**FUSE.** Ограничение из уточнения 2026-11-01 («для запуска нужен FUSE либо
`APPIMAGE_EXTRACT_AND_RUN=1`») снято для меню: если `libfuse2` не найден,
`install-appimage.sh --extract-and-run` пишет в `Exec=` строку
`env APPIMAGE_EXTRACT_AND_RUN=1`, и пункт меню запускается без FUSE, ценой распаковки
образа при старте. После установки `libfuse2` повторный запуск установщика возвращает
обычный `Exec=`. Сам файл остаётся AppImage: обновление — повторный запуск установщика,
`AppImageLauncher` по-прежнему не требуется.

Обёртка не публикуется ассетом релиза: стабильный URL
`raw.githubusercontent.com/ModernByte/orbitfm/main/install.sh` всегда ведёт на
актуальную версию, а конкретную версию выбирает `--release`, ассеты которой уже
проверяются по `SHA256SUMS`.

## Уточнение (2026-11-19, ред. 2): отказ от Flatpak

Flatpak существовал в проекте с 2026-10-22 как второй Linux-канал: манифест
`packaging/linux/org.modernbyte.OrbitFM.yml` (runtime `org.freedesktop.Platform` 25.08,
libmpv/libass/libplacebo из исходников), вендинг Cargo-исходников
`flatpak-cargo-sources.json`, скрипт `build-flatpak.sh` и чекер
`check-flatpak-sources.py`, сверявший вендинг с `Cargo.lock`. Публикация в Flathub не
выполнялась: артефакт собирался локально.

**Решение владельца (2026-11-19): канал удаляется из проекта полностью.** Что удалено:

- упаковка: манифест, `flatpak-cargo-sources.json`, `build-flatpak.sh`,
  `check-flatpak-sources.py`;
- CI: шаги «Check Flatpak manifest and vendored sources» и «Check Flatpak build
  script syntax» в джобе проверки упаковки; упоминание вендинга в комментарии
  `.github/dependabot.yml`;
- код: комментарий-заглушка о sandbox-признаке в `src/tray/sni.rs`;
- документация и вики: `docs/architecture/00-overview.md` (§7 модель поставки),
  `docs/CONTRIBUTING.md`, `docs/dev/README.md`, `docs/modules/12-tray.md`,
  `docs/ROADMAP.md`, `docs/VERSIONMAP.md`, `SECURITY.md`,
  `docs/ui/audio-reactive-globe.md`, `docs/audit/OrbitFM-future-features.md`,
  `docs/audit/OrbitFM-code-signing-and-notarization.md`, `README.md`, `README.ru.md`,
  руководство пользователя `docs/user/{en,ru}` (`install`, `panels`, `browser`,
  `troubleshooting`) и, как следствие, сгенерированная вики.

**Причины, а не только «не нужно»:**

1. **Песочница ломала продуктовый контракт.** IPC-сокет Flatpak-сборки живёт в
   приватном runtime-каталоге sandbox, поэтому виджет Noctalia, правила окон и
   команды `orbitfm ...` из терминала с такой сборкой не работают. Это не дефект
   упаковки, а следствие модели песочницы: продукт в ней работал неполно, и
   документация вынуждена была оговаривать это ограничение в пяти местах.
2. **Второй канал требовал постоянной синхронизации.** Манифест, вендинг
   Cargo-исходников и чекер надо было держать в согласии с `Cargo.lock` при каждом
   обновлении зависимостей — отдельный класс поломок, ловившийся только
   собственным скриптом.
3. **Канал не поставлялся.** Артефакт не публиковался ни в Flathub, ни в релизах;
   единственным потребителем был локальный запуск, для которого есть AppImage.
4. **Цена поддержки выше выгоды.** Один канал поставки на Linux даёт метаданные
   рабочего стола, rootless-установку и полный CLI/IPC — этого достаточно, чтобы
   закрыть сценарии пользователя.

**Что это не отменяет.** AppImage остаётся основным артефактом, MSI и DMG —
нативными установщиками; песочница как способ поставки не рассматривается, пока у
проекта нет сценария, в котором IPC и CLI доступны извне песочницы. Возврат к вопросу
возможен только новым ADR, а не восстановлением удалённых файлов.
