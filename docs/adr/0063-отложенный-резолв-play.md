# ADR-0063: Отложенный резолв `play <uuid>`

**Статус:** Принято  
**Дата:** 2026-11-12  
**Участники решения:** ModernByte Architecture

## Контекст

IPC-команда `play <uuid>` должна запускать станцию, которой может не быть ни
в результатах последнего поиска, ни в офлайн-снимке. До этой ревизии
Application Core вызывал `RadioBrowserClient::get_station` синхронно через
`runtime.block_on` прямо в `process_commands` (открытое окно) и в `park()`
(скрытое окно). Бюджет запроса — `STATION_LOOKUP_TIMEOUT = 8 с`; всё это
время кадр UI не рисовался, а парковка не обрабатывала другие события.

Аудит 0.22.0-rc.1 (§2.2.3, §2.4) справедливо отметил `block_on` на UI-пути.
Сам `audio.play` здесь не виноват: он возвращается после короткой команды
`loadfile`; виноват сетевой резолв станции.

Для `play-url` уже есть проверенный образец: резолв идёт в tokio-задаче,
`PendingStream` хранит запрос и канал, `tick()` или ветка `park()` забирают
результат и только потом отвечают клиенту (ADR-0040).

## Решение

### 1. Быстрый локальный путь

`Session::local_station(uuid)` ищет станцию в результатах последнего поиска и
в офлайн-снимке мира. Если UUID найден, `start_station` выполняется в текущем
кадре, ответ `ok`/`error` уходит сразу. Сеть не нужна.

### 2. Один фоновый поиск

Если станции нет локально, создаётся `PendingPlay { request, rx }`, а в
tokio-задачу уходит:

```rust
timeout(STATION_LOOKUP_TIMEOUT, radio.get_station(&uuid))
```

Задача будит GUI через `WakeHandle` и отправляет результат в канал. До
завершения поиска второй `play` получает
`error поиск станции уже выполняется` — как повторный `play-url`.

### 3. Забор результата

- Открытое окно: `Session::tick` вызывает `poll_play_lookup` после
  `process_commands`.
- Простой: `park()` добавляет ветку `Parked::Play`, `wait_on` слушает канал
  через `play_recv`.

`finish_play_lookup` забирает `PendingPlay`, запускает станцию и отвечает
клиенту строкой `ok` или `error <сообщение>`. Ответ приходит после
`start_station`, поэтому `ok` означает фактический запуск, а не «запрос
принят».

### 4. Границы контракта

- Текстовая команда и её аргумент не меняются.
- Схема `status --json` не меняется; `schema` остаётся 1.
- `execute(&IpcCommand::Play)` больше не выполняет резолв: команда
  перехватывается в `process_commands` и `park()`, как `play-url`.
- Бюджет ответа IPC (`APP_REPLY_TIMEOUT = 10 с`) по-прежнему больше бюджета
  поиска (8 с), поэтому клиент получает осмысленный `error`, а не обрыв.

## Альтернативы

| Вариант | Причина отклонения |
|---------|--------------------|
| Оставить `block_on` | 8 секунд замороженного кадра на каждый незнакомый UUID |
| `spawn_blocking` + ожидание в кадре | Не убирает ожидание, только меняет поток |
| Предзагружать все станции каталога | Каталог Radio Browser слишком велик для памяти и старта |
| Отвечать `ok` сразу, а станцию запускать позже | Нарушает контракт: `ok` должен означать выполненную команду |
| Несколько параллельных `play` | Ответы приходят не в порядке запросов; пользователь не понимает, какая станция играет |

## Последствия

**Положительные:**

- UI и парковка не блокируются сетью;
- поведение совпадает с `play-url`: один отложенный запрос, явная ошибка при
  повторе;
- `ok` по-прежнему означает запущенную станцию.

**Отрицательные:**

- ответ `play` может прийти через несколько секунд, если станции нет
  локально; это отражено в `docs/interfaces/05-ipc.md`;
- `PendingPlay` занимает место в `Session` до ответа или разрыва канала.

## Тестирование

- Локальный путь проверяется существующими тестами `start_station` и
  парсингом `IpcCommand::Play`.
- Отложенный путь проверяется вручную: `orbitfm play <uuid>` при скрытом
  окне не подвешивает `status`, а ответ приходит после резолва.
- `play_recv` с `None` даёт `error поиск станции завершился` — канал не
  оставляет клиента без ответа.
