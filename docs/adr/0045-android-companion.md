# ADR-0045: Android Companion — рамки v1

**Статус:** Принято  
**Дата:** 2026-11-03  
**Участники решения:** ModernByte Architecture

## Контекст

Desktop-контур OrbitFM насыщен: IPC, шеллы, browser companion, офлайн-снимок,
локализация, упаковка и мастер первого запуска закрыты в 0.17. Следующий рост —
слушание в кармане: дорога, работа, прогулка. Desktop остаётся «центром» с
глобусом, библиотекой и сложными фильтрами, но переносить весь 3D-стол на
телефон дорого и слабо оправдан на середине Android.

Аудит `docs/audit/OrbitFM-future-features.md` зафиксировал Android как
приоритет A. Нужно решить продуктовую роль, технический контур, общие
контракты с desktop и то, что сознательно не делается в v1.

## Решение

### 1. Продуктовая роль

Android v1 — **Companion player + library sync light**, а не клон desktop:

- сейчас играет / пусто;
- поиск по имени, стране и жанру через Radio Browser;
- фоновое воспроизведение через `MediaSessionService` и Foreground Service
  типа `mediaPlayback`;
- `MediaSession`: шторка, Bluetooth/наушники, базовый Android Auto;
- избранное и история локально;
- импорт библиотеки из desktop по схеме 1 (`docs/interfaces/15-library-export.md`);
- радиорулетка в упрощённом виде;
- настройки: системный язык, потолок битрейта, тема system/dark/light.

Полный 3D-глобус, собственный аккаунт, сервер синхронизации и дублирование
всех `WindowMode` — **не входят в v1** (см. § 5).

### 2. Технический контур

| Слой | Решение |
|------|---------|
| Язык и UI | Kotlin, Jetpack Compose |
| Плеер | Media3 (ExoPlayer), ICY-метаданные через `IcyHeaders`/`IcyInfo` |
| Фон | `MediaSessionService`, FGS `mediaPlayback`, постоянное уведомление |
| Сеть | OkHttp или Ktor; DNS discovery Radio Browser как на desktop |
| Данные | Room (избранное, история) и DataStore (настройки) |
| Карта v1.5 | MapLibre Native; платформенная карта допустима, если дешевле |
| Модули | `:app`, `:core:radio`, `:core:player`, `:feature:search` |
| DI | Один стиль на весь проект (Hilt или Koin); для v1 не принципиально |

Ориентиры версий на дату решения: Kotlin 2.4.x, Compose BOM 2026.09.x,
Media3 1.11.x, AGP 9.5.x, `minSdk 26`, `targetSdk 36`. Версии фиксируются в
`gradle/libs.versions.toml` Android-репозитория, а не в этом ADR.

**Связь с desktop-кодом:** прямой шаринг Rust UI не планируется. Общими
остаются правила: SSRF-политика URL, схема экспорта библиотеки, семантика
метаданных станции. Опциональный общий Rust-клиент каталога через `uniffi`
или JNI — возможное позднее решение, не блокер v1.

### 3. Общие контракты

- **Библиотека:** только файл схемы 1 из `docs/interfaces/15-library-export.md`.
  Импорт на Android проходит те же проверки, что desktop: публичный `http(s)`
  без userinfo, потолки размера и числа станций, санитизация строк, слияние по
  UUID с приоритетом локальной записи.
- **Radio Browser:** тот же продукт-токен User-Agent; для Android —
  `OrbitFM/1.0 (ModernByte; Android; Kotlin)`. Клик-трекинг остаётся
  документированным и отключаемым на уровне клиента.
- **Метаданные станции:** `stationuuid`, `name`, `url`, `url_resolved`,
  `countrycode`, `tags`, `bitrate`, `codec`, `source`; пустые поля не
  выдумываются.

### 4. Безопасность и магазины

- `https` по умолчанию; cleartext-потоки — только через явную запись
  `network_security_config` и с тем же классом запретов, что ADR-0025:
  никаких `file://`, link-local и приватных literal-адресов из
  пользовательских URL.
- Нет аккаунта, аналитики и отправки библиотеки на сервер.
- FGS объявляет `android:foregroundServiceType="mediaPlayback"` и разрешение
  `FOREGROUND_SERVICE_MEDIA_PLAYBACK`; уведомление соответствует политике
  Google Play.
- `targetSdk 36` — требование Play для новых публикаций с 31.08.2026.
- Лицензия Android-приложения и NOTICE магазина оформляются отдельно от MIT
  desktop-репозитория.

### 5. Что сознательно не делается в v1

1. Полный 3D-глобус на GLES/Vulkan.
2. Свой аккаунт и облачная синхронизация.
3. Все четыре `WindowMode` desktop.
4. Bar-плагины и интеграции оболочек.
5. Собственный сервер каталога: источник — публичный Radio Browser.

## Открытые решения владельца

| Вопрос | Варианты | На что влияет |
|--------|----------|---------------|
| Репозиторий | `ModernByte/orbitfm-android` или `android/` в monorepo | CI, релизы, лицензии, доступы |
| Языки v1 | en+ru или полный паритет 16 | объём переводов и QA |
| Карта | v1 или строго v1.5 | срок первой публикации |
| Магазин | GitHub APK / F-Droid / Google Play | подпись, политика, сроки |
| Синхронизация | только файл или сразу путь под Syncthing | UX импорта и документация |

Эти решения не меняют архитектурных рамок выше; они фиксируются отдельными
записями перед стартом Android-кода.

## Альтернативы

| Вариант | Причина отклонения |
|---------|--------------------|
| Полный порт desktop с 3D-глобусом | Дорого, тяжело на середине Android, не даёт ежедневной ценности |
| Только remote-пульт к домашнему desktop | Узкий сценарий, требует сети и доверия к домашнему хосту |
| WebView-обёртка вокруг desktop UI | Не даёт фонового аудио и MediaSession уровня Android |
| Свой аккаунт и синхронизация | Инфраструктура и приватность без доказанного спроса |
| Общий Rust UI через uniffi сразу | Блокирует v1; возможен позже для каталога |

## Последствия

**Положительные:**

- понятная граница «desktop — центр, Android — плеер»;
- перенос библиотеки опирается на уже реализованную схему 1;
- безопасность и магазинные требования зафиксированы до кода;
- desktop не обязан замирать: enablers уже в 0.18.

**Отрицательные / Риски:**

- два репозитория (или каталога) требуют синхронизации схемы экспорта;
- Media3 ICY и cleartext-потоки потребуют отдельного тестового набора;
- без общего Rust-ядра правила SSRF придётся реализовать на Kotlin и
  держать в синхроне с desktop;
- открытые решения владельца могут сдвинуть сроки первой публикации.
