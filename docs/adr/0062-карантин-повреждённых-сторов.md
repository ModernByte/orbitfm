# ADR-0062: Карантин повреждённых файлов состояния

**Статус:** Принято  
**Дата:** 2026-11-12  
**Участники решения:** ModernByte Architecture

## Контекст

`library.json` и `settings.json` пишутся атомарно (ADR-0013), поэтому
обрезанный JSON после сбоя питания маловероятен. Но файл может быть испорчен
вручную, сторонней утилитой или несовместимой схемой. До этой ревизии
`StationLibrary::load` и `SettingsStore::load` возвращали `Parse`, `main`
создавал ephemeral-стор и писал `warn!` в лог. Пользователь видел пустое
избранное и настройки по умолчанию без объяснения; повреждённый файл
оставался на месте, и следующая запись в эфемерный стор молча терялась.

`StatsStore` уже решает похожую задачу иначе (ADR-0049 §2): неразбираемый
файл не трогается до первой успешной записи, счётчики начинаются с нуля,
показывается тост. Для библиотеки и настроек важнее не оставить пользователя
без рабочего файла навсегда: после карантина стор должен снова уметь писать.

## Решение

### 1. Переименование, а не удаление

При ошибке разбора JSON файл переименовывается рядом:

```
library.json  → library.json.corrupt
              → library.json.corrupt-1
              → library.json.corrupt-2 …
```

`storage::quarantine` подбирает первое свободное имя и никогда не заменяет
существующую копию: прежний карантин — тоже пользовательские данные. Потолок
попыток — 100; исчерпание даёт ошибку, а не перезапись.

### 2. Рабочий путь после карантина

- `rename` удался → стор сохраняет исходный путь. Первая же запись создаёт
  свежий валидный файл, а повреждённая копия остаётся рядом для разбора.
- `rename` не удался → стор становится эфемерным (`path = None`). Это
  осознанно: писать поверх повреждённого файла нельзя, иначе данные будут
  потеряны безвозвратно.

Ошибки чтения (например, нет прав) не считаются повреждением: `load`
возвращает `Read`, и `main` по-прежнему создаёт ephemeral-стор. Карантин
касается только успешно прочитанного, но неразобранного JSON.

### 3. Наблюдаемость

Оба стора отдают:

```rust
pub fn damaged_at_load(&self) -> bool;
pub fn quarantined_path(&self) -> Option<&Path>;
```

`Session::new` показывает один тост на стор:

- `NoticeKey::LibraryDamaged` — «библиотека не читается, начата с нуля»;
- `NoticeKey::SettingsDamaged` — «настройки не читаются, взяты значения по
  умолчанию».

Если карантин удался, путь к копии уходит в `detail`. Если нет — тост
остаётся без пути: файл не тронут, и его судьба известна пользователю по
исходному расположению.

### 4. Мастер первого запуска

Повреждённые настройки считаются существующим профилем:
`existed_at_load = true`. Мастер первого запуска (ADR-0041) не показывается
повторно — пользователь уже настроил приложение, а потеря настроек не должна
выглядеть как первый запуск.

### 5. Что не меняется

- `stats.json` сохраняет поведение ADR-0049: счётчики с нуля, файл не
  трогается до успешной записи. Карантин к нему не применяется.
- Снимок мира и экспорт библиотеки не участвуют: у них свои контракты.
- Схема `status --json`, IPC и формат файлов не меняются.

## Альтернативы

| Вариант | Причина отклонения |
|---------|--------------------|
| Удалить повреждённый файл | Уничтожает данные, которые ещё можно спасти вручную |
| Оставить файл и писать поверх | Первая запись затирает повреждённые данные |
| Версионировать схему и мигрировать | Не помогает при синтаксической порче и ручных правках; карантин нужен в любом случае |
| Молча начать с нуля | Пользователь не понимает, куда делись избранное и настройки |
| Общий карантин для `stats.json` | Ломает уже принятое поведение ADR-0049 без выигрыша |

## Последствия

**Положительные:**

- повреждённые данные сохраняются рядом с рабочим файлом;
- стор снова становится записываемым без перезапуска;
- пользователь видит причину и путь к копии;
- тесты на битый JSON проверяют реальное поведение, а не только `Err`.

**Отрицательные:**

- рядом с файлами появляются копии `.corrupt*`, которые нужно чистить
  вручную;
- при неудачном `rename` (например, только чтение каталога) изменения живут
  до конца процесса — как и раньше.

## Тестирование

- `storage::quarantine_moves_damaged_file_without_clobbering` — вторая копия
  получает `-1`, первая цела.
- `storage::quarantine_reports_missing_file`.
- `library::corrupt_file_is_quarantined_and_starts_empty` — карантин, тост,
  свежая запись, повторная загрузка без повреждения.
- `settings::corrupt_file_is_quarantined_and_starts_from_defaults` — то же плюс
  `existed_at_load`.
- `settings::unknown_sleep_action_is_quarantined` — неизвестное значение
  трактуется как повреждение, а не как молчаливый сброс.
