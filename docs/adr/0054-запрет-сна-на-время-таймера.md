# ADR-0054: Запрет сна ОС на время таймера сна

**Статус:** Принято  
**Дата:** 2026-11-06  
**Участники решения:** ModernByte Architecture, владелец продукта

## Контекст

Таймер сна (ADR-0046) останавливает эфир по дедлайну, но ОС может уснуть
раньше: пользователь засыпает под радио, машина уходит в suspend, таймер
замирает вместе с ней. Владелец потребовал: «пока играет радио и таймер
считает, не давать ОС уйти в сон». Это требование помечено как важнейшее в
задаче.

Замеры и документация этой машины:

| Факт | Источник |
|------|----------|
| `mode=delay` бесполезен: `InhibitDelayMaxSec=` по умолчанию 5 с, затем операция выполняется всё равно | `man 5 logind.conf` |
| `mode=block` на `sleep` не блокирует закрытие крышки: `LidSwitchIgnoreInhibited=` по умолчанию `yes` | `man 5 logind.conf` |
| `delay` допустим только для `sleep` и `shutdown`; `idle`+`delay` — недопустимая комбинация | `man 1 systemd-inhibit` |
| `systemd-inhibit --list` на машине: 7 локов, ни одного `sleep/block` | замер |
| fd-лок logind живёт ровно пока открыт fd, поэтому `busctl call … Inhibit` не годится: fd умирает вместе с процессом `busctl` | `login1.Manager.Inhibit` возвращает `h` |
| Portal даёт только `Idle`; методов Suspend/PowerOff в портале нет | замер предыдущей сессии |

Решение владельца: ингибитор — дочерний `systemd-inhibit`, без новой
зависимости; `zbus` как прямая зависимость отклонён.

## Решение

### 1. Модуль `src/power/`

```
src/power/
├── mod.rs      # PowerInhibit, InhibitionGuard, InhibitBackend, detect()
├── linux.rs    # systemd-inhibit (дочерний процесс)
├── macos.rs    # caffeinate -i -w <pid> -t <secs>
├── windows.rs  # SetThreadExecutionState
└── fake.rs     # тестовый бэкенд без ОС
```

Публичная поверхность:

- `PowerInhibit::acquire(why) -> Result<InhibitionGuard, PowerError>`;
- `InhibitionGuard` освобождает лок в `Drop` (идемпотентно);
- `InhibitBackend::{LogindInhibit, Caffeinate, SetThreadExecutionState,
  Unavailable}` — для статуса и диагностики;
- `detect()` не спавнит процессов: только проверяет доступность способа.

### 2. Linux: дочерний `systemd-inhibit`

```
systemd-inhibit --what=sleep --who=OrbitFM --why="Radio sleep timer" \
                --mode=block sleep infinity
```

- argv фиксирован, shell не запускается — прецедент
  `apply_hyprland_rules()` (`src/integration/wm.rs`).
- Носитель лока — `sleep infinity`; при release дочерний процесс убивается
  (`kill` + `wait`), лок исчезает.
- Осиротевший лок недопустим: в `pre_exec` ставится
  `libc::prctl(PR_SET_PDEATHSIG, SIGKILL)` (`libc` уже в зависимостях).
  Родитель умер — носитель умирает, лок снимается.
- Проверка живости — `child.try_wait()` в `poll_sleep_events`, без нового
  таймера. Носитель умер ⇒ `NoticeKey::InhibitionLost`, повторно не тикаем.
- `busctl` для `Inhibit` неприменим (fd живёт в fd-таблице `busctl`);
  `zbus` отклонён владельцем — новая прямая зависимость ради одного вызова.

Ограничение честно фиксируется: `what=sleep`/`mode=block` **не** отменяет
закрытие крышки при `LidSwitchIgnoreInhibited=yes`. Задача формулировалась
как «не давать ОС уйти в сон», а не «игнорировать намерение пользователя
закрыть крышку»; `handle-lid-switch` сознательно не берём.

### 3. macOS и Windows

- macOS: `caffeinate -i -w <our_pid> -t <secs>` — новых crate нет.
  `-i` запрещает idle sleep, `-w` привязывает жизнь к нашему pid, `-t`
  страхует от вечного лока. `-d` (дисплей) не ставим.
- Windows: `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` из
  главного потока, release — `ES_CONTINUOUS`. Добавляются **features**, а не
  crate: `Win32_System_Power` (`Cargo.toml`). `ES_DISPLAY_REQUIRED` не ставим:
  гашение экрана — не наша задача.

### 4. Владение и состояние

- `Session::sleep_inhibition: Option<InhibitionGuard>` — не event loop окна:
  таймер живёт и в `tick()`, и в парковке (`park()`).
- Идемпотентная `Session::sync_inhibition()` вызывается из `tick()` после
  `poll_sleep_events()`, из `park()` рядом с `sync_tray`/`publish_status` и из
  `quit()`.
- Условие acquire: `timer_active && audio.state() != Stopped` — ровно
  формулировка владельца «пока играет радио и таймер считает».
- Release: таймер сброшен/истёк, эфир остановлен, процесс выходит, лок потерян.
- Отказ polkit/`systemd-inhibit` не фатален: таймер продолжает работать,
  `status --json` и раздел «Окно» показывают `Unavailable` + detail ошибки
  (`notice_text(..., Some(detail))`).

### 5. Наблюдаемость

- В `status --json` поле `sleep.inhibited: bool` (аддитивно, схема 1).
- В лог — одна строка `info!` при acquire/release и `warn!` при отказе;
  повторных строк на каждом тике нет.

## Последствия

**Положительные:**

- машина не засыпает, пока идёт ночной эфир по таймеру;
- нет новых crate и FFI для logind;
- лок гарантированно умирает вместе с процессом (`PR_SET_PDEATHSIG`);
- поведение тестируется без ОС через `power::fake`.

**Отрицательные / риски:**

- закрытие крышки всё равно усыпит машину — задокументировано;
- `systemd-inhibit` может отсутствовать в PATH (контейнер, не-systemd):
  тогда `Unavailable`, таймер работает без лока;
- macOS-ветка `caffeinate` и Windows-ветка требуют live-проверки на своих ОС.

## Альтернативы

| Вариант | Причина отклонения |
|---------|--------------------|
| `busctl call … Inhibit` | fd лока умирает вместе с `busctl`, блок исчезает сразу |
| `zbus` + `login1.Manager.Inhibit` | новая прямая зависимость ради одного вызова; отклонено владельцем |
| `mode=delay` | `InhibitDelayMaxSec=5` ⇒ не гарантия, операция выполнится |
| `handle-lid-switch` | отменяет намерение пользователя закрыть крышку |
| `IOPMAssertionCreateWithName` | новая FFI/core-foundation; дочерний `caffeinate` покрывает задачу |
| `ES_DISPLAY_REQUIRED` | гасить/не гасить экран — не задача таймера |
