# AGENTS.md — Правила работы AI-агентов OrbitFM

**Проект:** OrbitFM  
**Организация:** ModernByte (https://github.com/ModernByte)  
**Статус:** Обязателен для всех агентов  
**Последнее обновление:** 2026-11-03

Этот документ — единый источник правил для любого AI-агента, работающего с репозиторием.  
Нарушение правил считается дефектом работы агента.

---

## 1. Главные принципы

1. **Ничего не выдумывать.**  
   Любое техническое утверждение обязано опираться на:
   - официальную документацию **актуальных** версий (docs.rs, mpv client.h, docs.noctalia.dev, api.radio-browser.info, egui/eframe);
   - уже принятые ADR;
   - SRS (`orbitfm_srs.md`).

2. **Linux First.**  
   Все решения сначала проектируются и проверяются под Linux (Wayland: Niri, Hyprland).  
   Кроссплатформенность — вторична и не должна ломать Linux-путь.

3. **Именование ModernByte (строго).**

   | Сущность              | Значение                                      |
   |-----------------------|-----------------------------------------------|
   | Организация           | ModernByte                                    |
   | Репозиторий           | ModernByte/orbitfm                            |
   | Crate / binary        | orbitfm                                       |
   | Plugin ID (Noctalia)  | modernbyte/orbitfm                            |
   | app-id / Desktop Entry| org.modernbyte.OrbitFM                        |
   | User-Agent            | OrbitFM/1.0 (ModernByte; Linux; Rust)         |
   | Author в plugin.toml  | ModernByte                                    |

4. **Документировать решения.**  
   Значимые архитектурные выборы — только через ADR **до** написания кода.

5. **Не трогать лишнее.**  
   Не добавлять файлы, зависимости, feature-флаги и «заготовки на будущее» без явного запроса или ADR.

6. **Single-instance.**  
   Один процесс. Закрытие окна = Hide, не завершение процесса.

7. **Актуальные версии.**  
   Использовать последние стабильные версии Rust toolchain, crate’ов и внешних API, если иное не зафиксировано ADR. Перед добавлением зависимости — проверить docs.rs / crates.io на текущую major и breaking changes.

## 2. Команда субагентов и делегирование

Главный агент координирует. Узкие задачи делегируются через соответствующие скиллы.

| Роль / Скилл              | Зона ответственности                                      | Когда вызывать |
|---------------------------|-----------------------------------------------------------|----------------|
| **orbitfm-core**          | Базовые инварианты, именование, структура, запреты        | **Всегда** при любой задаче по OrbitFM |
| **orbitfm-architect**     | Архитектура, ADR, границы модулей, компромиссы            | Новые подсистемы, рефакторинг границ, ADR |
| **orbitfm-rust**          | Стиль Rust, async, FFI, ошибки, тесты, Cargo              | Любой Rust-код |
| **orbitfm-gui**           | eframe / egui / egui-wgpu, окно, глобус, PaintCallback    | UI и 3D |
| **orbitfm-audio**         | libmpv, play/stop/reconnect, FFT-метрики                  | Аудио |
| **orbitfm-radio**         | Radio Browser, discovery, User-Agent, click               | API станций |
| **orbitfm-geo**           | geo / geojson / rstar, raycasting, Point-in-Polygon       | Гео и выбор страны |
| **orbitfm-ipc**           | Single-instance, сокет/pipe, протокол команд              | IPC, CLI, lifetime процесса |
| **orbitfm-integration**   | Noctalia, MPRIS/playwire, window rules                    | Интеграции с окружением |
| **orbitfm-product**       | Продуктовые приоритеты, scope релизов, порядок волн        | Планирование релиза, оценка фичи, спор «что делать раньше» |
| **orbitfm-android**       | Android Companion: Kotlin/Compose, Media3, FGS, MediaSession | Любая работа по мобильному клиенту, mobile import и playback |
| **orbitfm-tui**           | `orbitfm-tui` на ratatui: IPC-клиент, экраны, визуализаторы | Проектирование, реализация и ревью TUI |
| **orbitfm-listening-ux**  | Sleep timer, очередь next/previous, network profile, stats, URL-алиасы | Изменение повседневных сценариев слушания на desktop и в Android |
| **orbitfm-library-portability** | Схема 1 export/import, слияние, URL-политика импорта | Формат библиотеки, Settings → Data, связка desktop ↔ Android |
| **orbitfm-docs**          | Синхронизация SRS, ADR, modules, interfaces, patterns, CHANGELOG | Любое изменение контрактов или документации |
| **orbitfm-patterns**      | Каталог паттернов, выбор структуры кода                   | Проектирование модулей, рефакторинг структуры |

### Правила делегирования

1. `orbitfm-core` подгружается **первым** при любой задаче.
2. Профильный скилл вызывается при входе в соответствующую подсистему по матрице §2.1.
3. `orbitfm-product` отвечает только за scope и порядок работ; он не отменяет принятый ADR и не расширяет полномочия на код.
4. Если задача затрагивает публичный контракт — обязательно `orbitfm-architect` + `orbitfm-docs` + профильный скилл.
5. Rust-код пишется только в связке `orbitfm-rust` + профильный скилл. Для Kotlin/Android обязателен `orbitfm-android`; `orbitfm-rust` к Kotlin не применяется.
6. Код TUI пишется в связке `orbitfm-tui` + `orbitfm-rust` + `orbitfm-ipc`.
7. При проектировании структуры модуля — `orbitfm-patterns` + `docs/patterns/00-overview.md`.
8. Субагент получает в задании явный список скиллов; отчёт начинается со строки «Скиллы: …».
9. Агент не имеет права «перепрыгивать» через ADR при спорных решениях.

### 2.2. Правила использования скиллов

Правила обязательны для главного агента и всех субагентов.

1. **Маршрут до работы.** Сначала `orbitfm-core`, затем основной скилл из §2.1 и его обязательные спутники. Порядок источников: принятый ADR → SRS → interfaces/modules → `SKILL.md` → общая практика.
2. **Конфликт скилла и ADR.** Если `SKILL.md` противоречит принятому ADR или интерфейсу, действует ADR; расхождение в скилле исправляется в той же задаче. Нельзя молча следовать устаревшему скиллу.
3. **Передача субагенту.** В задании перечисляются: загружаемые скиллы, обязательные документы, границы изменений и ожидаемый отчёт. Отчёт субагента начинается со строки «Скиллы: …»; отсутствие нужного скилла — дефект.
4. **Скилл не расширяет полномочия.** `orbitfm-product` не разрешает начинать код вне ROADMAP; `orbitfm-android` и `orbitfm-tui` не запускают реализацию без соответствующего ADR и решения владельца; `orbitfm-listening-ux` не ослабляет SSRF/publishable-политику.
5. **Минимальный набор.** Один основной скилл и только реально нужные поддерживающие, обычно не более двух сверх `orbitfm-core`; условные спутники из §2.1 подключаются лишь при соответствующем сценарии. На стыке подсистем основной — тот, чей контракт или поведение меняется. Не загружать скиллы «для галочки» и не пересказывать их в отчёте.
6. **Публичный контракт.** Любое изменение IPC, схемы, CLI, статуса или экспорта проходит через `orbitfm-architect` + `orbitfm-docs` и отражается в ADR/interface/module/CHANGELOG.
7. **Языки и платформы.** Rust — `orbitfm-rust`; Kotlin/Android — `orbitfm-android`; общие правила URL и схемы — из `orbitfm-library-portability`/`orbitfm-listening-ux`. Именование ModernByte из `orbitfm-core` действует везде.
8. **Достоверность источников.** Каждый скилл ссылается только на существующие пути репозитория и принятые ADR. Новый скилл или изменение маршрута требует записи в §2 и §8 и в CHANGELOG.
9. **Запрет на самовольную правку правил.** Субагент не меняет `docs/AGENTS.md`, принятые ADR и `.agents/skills/**` без явного указания владельца.
10. **Итоговый отчёт.** Главный агент указывает использованные скиллы, изменённые документы и выполненные проверки.

## 3. Источники истины (порядок чтения)

1. `orbitfm_srs.md`
2. `docs/architecture/00-overview.md`
3. Релевантные ADR в `docs/adr/`

## 4. Жёсткие правила модульности и расширяемости

### 4.1. Размер и структура файлов

**Принцип:** один файл — одна чёткая ответственность. Читаемость важнее «удобно всё в одном месте».

| Уровень | Порог | Действие |
|---------|-------|----------|
| Мягкий лимит | ~300–400 строк реализации | Выделить подмодуль или вынести тип/алгоритм |
| Жёсткий запрет | > 800–1000 строк | Только с явным ADR и обоснованием |
| Тесты | отдельно | `#[cfg(test)]` в том же файле — ок для unit; большие suites — `tests/` |

Дополнительно:

- Модуль = каталог или файл строго по `docs/modules/`.
- Публичная поверхность модуля **должна** соответствовать `docs/interfaces/`.
- `mod` / `pub mod` — явные; не делай `pub use` всего подряд.
- Вспомогательные функции, используемые только в одном месте, остаются приватными. Как только ими пользуются два модуля — вынос в общий узкий модуль с понятным именем.

**Признаки файла-монстра (немедленно дробить):**

- смешаны UI, domain и I/O;
- больше 5–7 публичных типов без общей темы;
- сложно описать содержимое файла одним предложением;
- при ревью невозможно удержать контекст в голове.

### 4.2. Зависимости между модулями

Строгая слоистая схема (зависимости только вниз):

```
Presentation (egui, render)
        ↓
Application Core (app state, routing)
        ↓
Domain Services (audio, radio, geo, media)
        ↓
Infrastructure (reqwest, libmpv FFI, sockets, playwire)
```

Конкретные запреты:

| Модуль | Не должен знать про |
|--------|---------------------|
| `audio` | egui, wgpu, Station UI, Noctalia |
| `radio` | libmpv, egui, window |
| `geo` | станции, аудио, UI |
| `render` | Station, AudioEngine, RadioClient |
| `ipc` | бизнес-логику play/search (только команды → App) |
| `media` | прямые вызовы libmpv (только через события/команды App) |

Циклические зависимости запрещены. Если A нужен B, а B нужен A — вынести общий контракт в interfaces / тонкий shared-модуль или пересмотреть границы (ADR).

### 4.3. Расширяемость

- Новая возможность → новый модуль **или** расширение существующего **без** ломки публичных интерфейсов.
- Ломающее изменение контракта → ADR + запись в VERSIONMAP/CHANGELOG.
- Опциональные части — feature-флаги (`mpris`, `fft`, `noctalia`, …).
- Composition over inheritance; маленькие сфокусированные трейты лучше одного «делает всё».
- Точки расширения (новый источник станций, новый бэкенд медиа) — через трейт + одну реализацию по умолчанию.

### 4.4. Запрещено в модульности

- God-object / God-file / «utils.rs на 2000 строк»
- Временные свалки, которые никто не убирает
- `pub` на всём подряд «чтобы удобно»
- Смешивание UI, domain и infrastructure в одном файле
- Скрытые зависимости через глобалы без крайней нужды и ADR

## 5. Правила производительности и памяти (обязательны с первого дня)

Код пишется сразу с учётом практик, доказавших эффект в высоконагруженных системах (в том числе опыт Cloudflare: отказ от лишней capacity, плоские буферы, упаковка enum, битфлаги, меньше мелких аллокаций → существенная экономия RAM).

Цель не «микрооптимизировать всё», а **не раздувать память и аллокации по привычке**.

### 5.1. Владение данными после создания — `Vec` → `Box<[T]>`

`Vec<T>` хранит `(ptr, len, capacity)`. После того как данные собраны и больше не растут, capacity не нужна: лишние 8 байт метаданных на 64-bit **и** часто неиспользуемая ёмкость в куче.

```rust
// Плохо: кэш станций больше не меняется, но держит capacity
let cache: Vec<Station> = fetch_all().await?;

// Хорошо: точный срез, меньше метаданных, нет лишней ёмкости
let cache: Box<[Station]> = fetch_all().await?.into_boxed_slice();
```

Применяй к: кэшу станций, спискам после discovery, загруженным геоданным (если дальше только read), статическим таблицам.

Не применяй слепо там, где коллекция продолжает расти (буфер IPC-команд, накопление кадров).

### 5.2. Плоские структуры (flat slicing) вместо роя мелких аллокаций

Много мелких `Vec`/`Box`/`String` → много аллокаций, больше метаданных, padding между объектами, давление на аллокатор и фрагментация.

Предпочитай:

- один непрерывный буфер + индексы/смещения;
- структуру «заголовок + payload в одном allocation», где это естественно;
- arena / bump для данных с одинаковым временем жизни (если профит ясен).

```text
Вместо: Vec<Vec<Point>> для полигонов стран
Лучше:  points: Box<[Point]>,  polygons: Box<[(start, len)]>
```

Одна (или мало) аллокаций вместо сотен.

### 5.3. Тяжёлые варианты enum — вынос в `Box`

Размер enum = размер самого большого варианта (+ тег). Если один вариант «жирный», **все** элементы коллекции платят за него.

```rust
// Плохо: Simple занимает столько же, сколько Heavy
enum Msg {
    Simple,
    Heavy { payload: [u8; 4096], meta: Meta },
}

// Хорошо
enum Msg {
    Simple,
    Heavy(Box<HeavyPayload>),
}
```

Особенно важно для очередей событий, IPC-сообщений, кэшей неоднородных объектов.

### 5.4. `Option` и битфлаги

- Редко присутствующие данные — `Option<T>` (для больших T — `Option<Box<T>>`).
- Несколько `bool` в структуре часто дают 1 байт + padding каждый. Упаковывай в флаги:

```rust
bitflags::bitflags! {
    #[derive(Clone, Copy)]
    struct StationFlags: u8 {
        const HAS_FAVICON = 0b0001;
        const IS_HTTPS    = 0b0010;
        const HIDE_BROKEN = 0b0100;
    }
}
```

Либо ручная битовая маска в `u8`/`u16`.

### 5.5. Устранение лишнего padding и компактные структуры

- Порядок полей влияет на размер: проверяй `std::mem::size_of`.
- Когда размер критичен (много маленьких записей), допустимо компактное представление (`[u8; N]` + безопасный разбор), **только** если есть измеримая выгода, инварианты гарантированы типами/тестами, а `.unwrap()` после проверки явно помечен как безопасный.

Не превращай весь код в ручную упаковку байтов ради 2% в холодном пути.

### 5.6. Меньше мелких аллокаций

- **Горячий путь (кадр UI, raycasting, парсинг ответа API в цикле):** ноль или минимум аллокаций.
- Переиспользуй буферы: `buf.clear(); buf.reserve(n);`.
- Строки: `&str`, `Cow<'_, str>`, `Arc<str>` — когда владение разделяется и данные иммутабельны.
- Не клонируй `String`/`Vec` «на всякий случай».

### 5.7. Алгоритмическая разумность

Не умножай размер вспомогательных структур без оценки выигрыша.

Антипаттерн: 10× виртуальных узлов / точек / кэш-записей дают крошечный прирост качества при кратном росте памяти. Ищи локальный оптимум.

В OrbitFM это относится к:

- размеру кэша станций;
- детализации геодатасета (110m vs 50m/10m);
- числу временных буферов в рендере.

### 5.8. Безопасность оптимизаций

- `.unwrap()` / `.expect()` — только при **доказанном** инварианте и с коротким комментарием.
- Сначала ясность и границы модулей, потом микрооптимизации в **горячих** местах.
- Оптимизация, которую нельзя объяснить в двух предложениях и покрыть тестом, — подозрительна.

### 5.9. Где применять в первую очередь (OrbitFM)

| Данные / путь | Рекомендация |
|---------------|--------------|
| Кэш станций после загрузки | `Box<[Station]>` или плоский буфер |
| Гео-полигоны + R-Tree | offline, минимум аллокаций на запрос; плотная укладка точек |
| События audio / IPC | компактные enum, `Box` на тяжёлые варианты |
| Кадр egui + globe | без аллокаций в `logic`/`ui`/`paint` на кадр |
| Конфиг после parse | `Box<[T]>`, `Arc<str>` для разделяемых строк |
| Редкие ошибки, init | оптимизировать не обязательно |

### 5.10. Чего не делать

- Оптимизировать вслепую без понимания, горячий ли путь.
- Жертвовать границами модулей ради «сэкономить один Box».
- Вводить unsafe ради упаковки без тестов и комментариев Safety.
- Хранить `Vec` с огромной capacity «про запас» у иммутабельных данных.

## 6. Процесс разработки (для агентов)

### 6.1. Порядок работы над задачей

1. Прочитать источники истины (раздел 3).
2. Определить затронутые модули и скиллы.
3. Если меняется архитектура / публичный контракт → ADR (статус «Предложено») **до** кода.
4. Обновить `docs/interfaces/` и/или `docs/modules/` при изменении контракта.
5. Реализация (маленькими логическими шагами).
6. Тесты.
7. Обновить CHANGELOG, ROADMAP, VERSIONMAP при необходимости.
8. Проверки: `cargo fmt`, `cargo clippy`, `cargo test`.

### 6.2. Git

- Ветки: `feature/...`, `fix/...`, `docs/...`, `adr/...`
- Коммиты: осмысленные, желательно Conventional Commits. Допустимы русский и английский.
- Один логический кусок — связанные коммиты, без «заодно поправил всё».
- Не коммитить: `target/`, артефакты поиска, секреты, большие бинарники без обоснования.

### 6.3. Документация

- Язык документации — **русский**.
- Изменился контракт → interfaces + modules + (при необходимости) ADR + CHANGELOG.
- Новый ADR → запись в CHANGELOG.
- Закрытый пункт ROADMAP → отметить `[x]`.

### 6.4. Код-стайл (кратко; детали в orbitfm-rust)

- Edition 2024, rustfmt, clippy.
- Ошибки: `thiserror` в модулях, `anyhow` на границах.
- `unwrap`/`expect` — только в main/тестах или при доказанном инварианте.
- Весь `unsafe` — минимальный и с комментарием «почему безопасно».
- Зависимости — **последние стабильные** версии, если иное не зафиксировано ADR.

## 10. Итог

Агент, работающий по этим правилам:

- пишет модульный, расширяемый код без файлов-монстров;
- не раздувает память лишними `Vec`, жирными enum и мелкими аллокациями;
- держит документацию и код в синхроне;
- делегирует узкие задачи правильным скиллам;
- использует актуальные версии зависимостей;
- не принимает архитектурных решений втихаря.

**Соблюдение этого документа обязательно.**
