# OrbitFM — архитектурный и security-аудит

**Репозиторий:** https://github.com/ModernByte/orbitfm  
**Проверенная ревизия:** `71e9bd83293c6fdeba1f09c5154f146124dabfb5` (`main`, 2026-10-28)  
**Версия проекта:** `0.12.0-rc.2`  
**Тип проверки:** статический обзор исходников, тестов, CI и документации GitHub.  
**Ограничение:** команды `cargo test`, `cargo clippy`, сборка и динамические сетевые тесты в этой сессии не запускались. Поэтому CI-конфигурация описывает предусмотренные проверки, но не подтверждает, что текущая ревизия прошла их успешно.

## 1. Executive summary

OrbitFM — нативный кроссплатформенный desktop-плеер интернет-радио на Rust, `eframe/egui`, `wgpu` и `libmpv`. Основная продуктовая идея — исследование станций через интерактивный 3D-глобус, с несколькими режимами окна и интеграцией с системными медиа-контролами.

**Общая оценка:** архитектура хорошо документирована для проекта такого размера; есть ADR, контракты модулей, тесты для критичных механизмов, CI с форматированием, Clippy и тестами. Отдельный ADR-0025 показывает осознанный подход к безопасному декодированию favicon.

**Главные замечания:**

1. **Подтверждённый риск неограниченного роста favicon-кэша/очереди.** Лимит 256 записей не является жёстким: если вытеснить `Queued`/`Loading` записи нельзя, `texture()` всё равно добавляет новую запись и URL в `pending`. См. `src/ui/images.rs:78-99`, `146-160`. Это потенциальный DoS по памяти/сетевым задачам при большом потоке уникальных URL.
2. **Подтверждённая неполная защита сетевой цели favicon.** Проверяется схема `http/https`, но не блокируются loopback, link-local, private IP и внутренние имена; разрешены редиректы, конечная цель каждого редиректа отдельно не проверяется. См. `src/app.rs:1297-1301`, `170-175`. Для desktop-клиента это не классический серверный SSRF, но остаётся вектор обращений к локальным/внутренним сервисам и сетевого трекинга.
3. **Защита декодера изображений в целом продуманная:** лимит ответа 512 KiB, сторона до 512 px, лимит аллокаций 8 MiB, allowlist PNG/JPEG/WebP, таймаут 6 секунд, до 3 редиректов, `catch_unwind`, оригиналы не сохраняются. См. `src/app.rs:203-242, 1320-1335`, `src/ui/images.rs:163-212`, `Cargo.toml:32`.
4. **Документация содержит рассинхронизацию:** `docs/architecture/00-overview.md:103` описывает favicon как `png/ico`, тогда как фактическая зависимость и ADR-0025 допускают JPEG/PNG/WebP и запрещают ICO.
5. **Есть риск сопровождения крупных файлов:** `src/ui/widgets.rs` — 1814 строк, `src/render/motion.rs` — 1500, `src/app.rs` — 1381. Это не дефект само по себе, но повышает стоимость изменений и вероятность конфликтов.
6. **CI не запускает заявленный в CONTRIBUTING `cargo deny check`** и в видимой конфигурации не выполняет `cargo audit`/SBOM-проверку. См. `docs/CONTRIBUTING.md:30-37`, `.github/workflows/ci.yml`.

## 4. Security-аудит обработки favicon/изображений

### 4.1 Модель угроз

OrbitFM не предоставляет серверную загрузку файлов пользователями и не сохраняет оригинальные изображения. Favicon скачивается автоматически по URL, пришедшему вместе с данными радиостанции. Поэтому актуальные угрозы отличаются от типичного backend upload endpoint:
- вредоносный или повреждённый файл для эксплуатации декодера;
- decompression bomb и чрезмерная аллокация;
- чрезмерно большой/медленный HTTP-ответ;
- подмена `Content-Type` и несоответствие сигнатуры;
- сетевые запросы к неожиданным адресам, включая localhost/private network;
- исчерпание памяти через очередь и кэш уникальных URL;
- отслеживание пользователя запросами к внешним доменам.

### 4.2 Защитные меры, которые подтверждаются кодом

| Мера | Реализация |
|---|---|
| Только HTTP(S) | `src/app.rs:1297-1301` |
| Таймаут запроса 6 секунд | `src/app.rs:42-45, 170-175` |

| MIME allowlist | `src/app.rs:46-52, 1303-1317`; `application/octet-stream` допускается, но содержимое всё равно декодируется по формату |
| Ограничение Content-Length и фактически прочитанных байтов до 512 KiB | `src/app.rs:1320-1335` |

| Размер каждой стороны до 512 px | `src/ui/images.rs:175-180, 207-212` |
| Лимит аллокаций декодера 8 MiB | `src/ui/images.rs:22-23, 207-212` |
| Ограничение параллельных загрузок до 8 | `src/ui/images.rs:16-17, 106-124` |

**Вывод:** базовая защита от вредоносных форматов и простых decompression bomb реализована существенно лучше, чем в типичном MVP. Не следует называть сам факт скачивания внешних картинок уязвимостью: в коде есть реальные ограничения и декодирование не делегируется браузеру.

### 4.3 SEC-01 — лимит кэша можно обойти (подтверждено кодом)

**Файлы:** `src/ui/images.rs:78-99`, `src/ui/images.rs:146-160`.

`texture()` при достижении `MAX_CACHED = 256` вызывает `evict()`. Однако `evict()` удаляет запись только если найдена запись не в состояниях `Queued`/`Loading`, и может не найти подходящего кандидата. После этого `texture()` всё равно вставляет новую запись и URL в `pending`. Поэтому `MAX_CACHED` ограничивает только обычный случай, но не является инвариантом размера коллекций.

Это особенно заметно, если UI быстро просматривает множество уникальных станций, а сеть медленная/недоступна: активные запросы и queued-записи не вытесняются, новые URL продолжают добавляться. `pending` и `entries` могут расти, а `take_fetches()` ограничивает только количество запросов одновременно, не общую очередь.

**Воздействие:** повышенное потребление памяти, длительный хвост фоновых запросов, лишняя работа UI и сетевой стек. Это denial-of-service на уровне доступности клиента при большом количестве уникальных URL; не RCE.

**Рекомендации:**
1. Сделать жёсткую верхнюю границу: если нет вытесняемой записи, не добавлять URL в кэш/очередь.
2. Ограничить длину `pending` и использовать bounded channel вместо `mpsc::unbounded_channel` для результатов (`src/ui/images.rs:45-46, 57`).
3. При вытеснении `Queued`-элемента удалять его из очереди; для `Loading` — отменять задачу либо игнорировать результат по generation/token.
4. Добавить регрессионный тест: создать существенно больше `MAX_CACHED` уникальных URL до завершения загрузок и assert, что `entries`/`pending` не превышают лимит.
5. Добавить тест на множество завершившихся результатов после вытеснения, чтобы результат старого запроса не воскрешал запись и не расходовал не тот слот.

### 4.4 SEC-02 — запросы к локальным/внутренним адресам (подтверждённый пробел защиты)

**Файлы:** `src/app.rs:1297-1301`, `src/app.rs:170-175`, `src/app.rs:203-237`. Риск также прямо отмечен в `docs/adr/0025-безопасная-обработка-favicon.md` в разделе «Отрицательные / Риски».

Проверка URL ограничивает только схему. Не видно блокировки:
- `127.0.0.0/8`, `::1`;
- RFC1918 IPv4, IPv6 ULA;
- link-local и cloud metadata endpoints;
- `.localhost`, внутренние hostnames и нестандартные числовые представления адресов.

HTTP-клиент допускает до трёх редиректов, но `favicon_url_allowed()` вызывается перед первоначальным `GET`, а не повторно для каждой цели редиректа. Таким образом, URL на публичном сервере потенциально может перенаправить запрос на внутреннюю цель.

**Контекст риска:** это десктопный клиент, а не сервер, доступный атакующему через публичный API; поэтому не следует автоматически классифицировать это как классический SSRF с высоким impact. Но каталог станций и favicon URL являются недоверенными данными, а запрос выполняется с сетевыми правами пользователя. Возможны обращения к локальным веб-интерфейсам, probing внутренней сети, побочные эффекты GET-запросов и сетевой tracking.

**Рекомендации:**
1. Если продукту не нужны локальные favicon-hosts, блокировать loopback/private/link-local/unspecified/multicast адреса.
2. Проверять каждую redirect-цель до её запроса либо отключить автоматические редиректы и реализовать ограниченное следование вручную.
3. Защититься от DNS rebinding: проверять разрешённые IP на каждом переходе и учитывать все A/AAAA-адреса; одного текстового сравнения hostname недостаточно.
4. Отдельно решить, нужен ли plain HTTP. Предпочитать HTTPS; HTTP оставить только при явной необходимости и с пониманием риска подмены изображения.
5. Добавить тесты для IPv4/IPv6 loopback, private/link-local, DNS-имён localhost, редиректа public → private, цепочки редиректов и DNS-переключения.
6. Не логировать полный URL с query-параметрами без редактирования: URL может содержать tracking tokens.

### 4.5 Остаточные риски обработки изображений

- `application/octet-stream` разрешён. Это допустимо, потому что фактический формат затем проверяется декодером, но стоит документировать именно такую двухступенчатую модель.
- MIME без заголовка разрешён (`src/app.rs:1313-1317`); это безопасно только при сохранении проверки сигнатуры, которая сейчас присутствует.
- `catch_unwind` перехватывает unwind-панику, но не защищает от abort, зависания нативного кода или исчерпания ресурсов ОС. Лимиты заметно снижают риск, но не дают математической гарантии.
- `image::Limits` — важный defense-in-depth, но обновления crate `image` и его декодеров должны сопровождаться dependency review и fuzz/regression tests.
- Оригиналы не пишутся на диск — поэтому path traversal, случайные имена файлов, EXIF-cleanup отдельным шагом, upload storage, CSP и `nosniff` для текущей реализации не являются применимыми контролями.

## 5. Архитектура и модульность

### Сильные стороны

- В документации заявлена однонаправленная слоистая архитектура: Presentation → Application → Domain → Infrastructure (`docs/architecture/00-overview.md:27-63`).
- `Session` переживает закрытие окна, а UI пересоздаётся при показе; это снижает риск привязки состояния воспроизведения к жизненному циклу окна (`docs/architecture/00-overview.md:66-88`).
- IPC отделён от бизнес-логики; сервер ограничивает подключения, размер команды и таймаут чтения (`src/ipc/server.rs:16, 91, 141-160`).
- На Unix сокет устанавливает права `0600`; lock-файл также создаётся с `0600` (`src/ipc/socket.rs:85-115, 150-179`).
- Поиск использует generation/revision и асинхронные каналы, чтобы не блокировать UI (`src/session/search.rs:82-109, 253-305`).
- Settings нормализуют ряд пользовательских значений и используют временный файл с последующим rename (`src/settings/mod.rs:378-393`).
- Архитектурные решения вынесены в ADR; интерфейсы и спецификации модулей имеют отдельные каталоги.

### MAINT-01 — чрезмерный размер отдельных модулей

- `src/ui/widgets.rs` — 1814 строк.
- `src/render/motion.rs` — 1500 строк.
- `src/app.rs` — 1381 строка.
- `src/services/radio_browser.rs` — 759 строк.
- `src/settings/mod.rs` — 685 строк.

Это не автоматически «плохая архитектура»: в Rust приватность и модульные границы могут быть важнее количества файлов. Однако самые крупные файлы объединяют много причин изменения и увеличивают когнитивную нагрузку при code review.

**Рекомендации:**
- Разделить `widgets.rs` по семействам UI/отрисовки, оставив тонкий фасад `ui::widgets`.
- Выделить из `app.rs` компонент загрузки favicon с отдельным HTTP policy, декодером и тестируемым bounded cache.
- Разделить `motion.rs` на типы/математику, state machine и uniform packing, сохранив API фасада.
- Сначала фиксировать границы тестами и контрактами, затем переносить код без одновременного UX-рефакторинга.

## 6. Code quality и тестирование

### Положительные признаки
- `Cargo.toml` фиксирует Rust edition 2024 и MSRV 1.95.
- CI запускает `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings` и `cargo test --all-targets` на Linux; macOS также проходит fmt/Clippy/test/build, Windows — fmt/Clippy/check и отдельную MSI-сборку (`.github/workflows/ci.yml`).

### QA-01 — отсутствует автоматический аудит зависимостей в CI

`docs/CONTRIBUTING.md:30-37` требует `cargo deny check`, но видимый `.github/workflows/ci.yml` выполняет fmt/Clippy/tests и не запускает `cargo deny`. Не обнаружен отдельный workflow для `cargo audit` или SBOM. В корне по изученному дереву также не виден `deny.toml`.

**Рекомендации:**
1. Добавить `cargo deny check` с конфигурацией для advisories, licenses, bans и sources.
2. Добавить `cargo audit` (или эквивалентный dependency scanner) в CI и регулярный scheduled run.
3. Собирать SBOM для release artifacts; сохранять результаты dependency scan как CI artifact.
4. Зафиксировать версии GitHub Actions через full commit SHA для supply-chain hardening. Сейчас CI использует теги вроде `actions/checkout@v4`, `dtolnay/rust-toolchain@stable`, `Swatinem/rust-cache@v2`.
5. Проверить релизный workflow на минимальные permissions, изоляцию публикации от pull_request и отсутствие исполнения недоверенного кода с release credentials.

### Дополнительные тесты, которых не хватает

- интеграционные тесты HTTP favicon-клиента с локальным mock server: timeout, 404, неверный MIME, отсутствующий MIME, chunked body больше лимита, `Content-Length` больше лимита, редиректы и redirect loop;
- property-based/fuzz тесты декодера на случайных и специально повреждённых PNG/JPEG/WebP;
- тест, подтверждающий жёсткую границу `MAX_CACHED`;
- тесты поведения IPC с некорректными/частичными сообщениями и конкурирующими клиентами;
- platform runtime tests для Windows SMTC и macOS Now Playing (в ROADMAP часть этих проверок остаётся открытой).

- resize до 64×64 после декодирования (`src/ui/images.rs:188-197`);
- LRU-подобное вытеснение по `last_used` (`src/ui/images.rs:146-160`);
- поиск и сетевые операции вынесены в async tasks (`src/session/search.rs:253-305`);
- IPC имеет `MAX_CONNECTIONS = 64`, таймауты и лимит размера команды (`src/ipc/server.rs:16, 141-199`).

### Основные риски
- неограниченная очередь favicon (SEC-01) нивелирует защиту по параллелизму;
- `UnboundedSender/Receiver` для результатов не ограничивает backlog при проблемах с обработкой результатов;
- в `src/app.rs` оркестрация UI и сетевой favicon-пайплайн сосуществуют в большом файле, что затрудняет независимые benchmark и fault-injection;
- не обнаружены benchmark/criterion сценарии для времени отрисовки глобуса, CPU/GPU-профиля анимаций или memory footprint при длительной работе. Это не означает, что производительность плохая — лишь что в проверенной области нет подтверждения измерениями.

**Рекомендации:**
- bounded queue + backpressure, метрики cache hit/miss, rejected URLs, timeout/error count;
- ограничить общее число уникальных favicon, которые можно запрашивать за один сеанс/в единицу времени;
- измерять FPS/CPU/GPU/память в Focus, Overlay, Listening и Panel, включая 1000+ станций и отключённые анимации;
- добавить stress test на долгую сессию и переключение между большим количеством стран;
- использовать профилирование прежде, чем менять алгоритмы рендера.

## 8. Документация

### Сильные стороны
- README покрывает функциональность, платформы, установку, быстрый старт, управление, настройки, интеграции и troubleshooting.
- Есть `docs/architecture`, `docs/modules`, `docs/interfaces`, `docs/patterns`, 36+ ADR, roadmap, changelog, wiki и contribution guide.
- ADR-0025 хорошо документирует threat model, форматный allowlist, лимиты и сознательные компромиссы.

### DOC-01 — устаревшее описание favicon

`docs/architecture/00-overview.md:103` говорит `reqwest + image (png/ico)`, а `Cargo.toml:32` включает `jpeg`, `png`, `webp`; `src/ui/images.rs:200-205` принимает PNG/JPEG/WebP. ADR-0025 также прямо говорит, что ICO не поддерживается. Это фактическое противоречие и может привести к ошибочному ожиданию поддержки форматов.

**Рекомендация:** заменить на `JPEG/PNG/WebP`, добавить проверку документации в merge checklist или отдельный smoke test, проверяющий критичные таблицы README/architecture против реальных feature flags.

### Другие замечания по документации
- `docs/CONTRIBUTING.md` заявляет Clippy `pedantic` «где уместно» и `cargo deny`, но CI явно включает `-D warnings`, не `-W clippy::pedantic`, и не запускает `cargo deny`. Стоит согласовать ожидания и автоматизацию.
- ADR-0025 честно отмечает отсутствие запрета приватных сетевых целей; после принятия hardening-решения ADR следует обновить вместе с тестами.
- Продуктовая документация должна явно различать «собирается в CI», «проверено вручную в runtime» и «заявлена поддержка».

## 9. План исправлений

### P1 — до следующего широкого релиза
1. Исправить жёсткую границу `FaviconCache`: при достижении лимита не добавлять запись, если нет безопасного кандидата на вытеснение.
2. Ограничить `pending` и канал результатов; обработать устаревшие ответы и отмену задач.
3. Решить сетевую политику favicon: блокировать внутренние диапазоны и перепроверять redirect destination либо документированно принять этот риск.

### P2 — следующий инженерный цикл
4. Добавить интеграционные HTTP-тесты favicon и fuzz/regression тесты декодера.
5. Подключить `cargo deny` и dependency vulnerability scanning в CI.
6. Вынести favicon loader из `app.rs` в изолированный сервис с инъекцией HTTP-клиента и bounded scheduler.
7. Провести runtime-проверки Windows SMTC/macOS Now Playing и добавить воспроизводимые smoke-test инструкции.

### P3 — улучшение сопровождения
8. Исправить `docs/architecture/00-overview.md:103`.
9. Разбить крупные UI/render модули на тематические подмодули без изменения поведения.
10. Добавить performance baseline и memory stress test для долгих сессий.

## 10. Итог

OrbitFM выглядит как зрелая для prerelease desktop-кодовая база с сильной документационной дисциплиной и заметно продуманной защитой favicon-декодера. По проверенным файлам **не обнаружено оснований утверждать, что загрузка favicon приводит к исполнению активного SVG-контента или что оригиналы сохраняются на диск**: SVG/GIF/ICO не входят в allowlist, оригинальные байты преобразуются в RGBA, присутствуют ограничения размера и разрешения.

Два пункта заслуживают первоочередного внимания: **нежёсткий лимит кэша/очереди** и **отсутствие сетевого ограничения на локальные/private targets с учётом редиректов**. Первый подтверждён непосредственно алгоритмом кэша. Второй — подтверждённый пробел в защитных проверках и потенциальный сетевой риск в desktop-контексте, а не доказанная возможность компрометации.

Перед релизом рекомендуется закрыть P1, добавить регрессионные тесты, включить dependency scanning и синхронизировать документацию с фактическим allowlist.
