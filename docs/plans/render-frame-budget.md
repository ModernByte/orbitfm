# План: дисциплина кадров и батч-проекция маркеров

| Поле | Значение |
|---|---|
| **Статус** | Волна 0 сделана (инструментация и baseline), волны 1–6 не начаты |
| **Дата** | 2026-11-12 |
| **База** | `0.22.0-rc.2`, коммит `6c36f97` |
| **Связанные ADR** | ADR-0059 (GPU и бюджет рендера), ADR-0060 (геометрия управления), ADR-0028 (движение глобуса), ADR-0012 (маркеры), ADR-0035 (тепловая карта) |
| **Входные материалы** | `src-patches/soa-batch-projection.patch`, `src-patches/marker-batch-vectorization.patch`, `src-patches/OrbitFM-marker-vectorization.md` |
| **Целевой релиз** | следующий минор после `0.22.0`; версия — по решению владельца |

**Коротко:** сначала baseline и span'ы, затем политика `request_repaint*`,
затем батч-проекция маркеров с переиспользуемыми буферами и кэшем unit-координат,
и только по замеру — dirty uniform / starfield / SIMD. Патчи из `src-patches`
считаются предложением: их нужно доработать и проверить, а не вливать как есть.

## 1. Задача

Сделать кадр глобуса предсказуемым: дешёвый idle, стабильный бюджет на слабом
CPU/iGPU и отсутствие лишних пробуждений окна. Главный рычаг в OrbitFM —
**«реже и меньше»**: политика `request_repaint*`, кэш неизменяемых данных,
один проход проекции маркеров. Микрооптимизация и смена графического стека —
только после замера.

**Цель:**

1. Измерить текущий кадр и зафиксировать baseline до любых правок.
2. Свести все пути перерисовки к явным режимам Asleep / Breathing / Auto-spin /
   Soft / Play / `reduce_motion` и убрать лишние immediate-кадры.
3. Внедрить батч-проекцию маркеров с одной `view_proj` на кадр и
   переиспользуемыми буферами, не меняя визуальную семантику.
4. Кэшировать unit-координаты станций и флаги `playing`/`selected` до смены
   списка или выбора.
5. Оставить GPU-пасс, текстуры и шейдер без переписывания: они уже уложены в
   бюджет ADR-0059.

**Не входит в этот план:**

- переписывание на `ash`/`vulkano`, смена `eframe`/`wgpu`;
- continuous rendering «чтобы шар крутился гладко»;
- GPU-проекция маркеров и readback;
- ручной SIMD (`std::simd`, `wide`, intrinsics) до профиля;
- новые зависимости;
- LOD, скрывающий станции, без отдельного решения владельца;
- визуальный редизайн маркеров, стран, звездного фона.

## 2. Доказательная база

### 2.1. Что уже измерено (ADR-0059)

| Факт | Значение |
|---|---|
| Подготовка детального яруса Земли | было 541 мс в кадре, стало медиана 0,02 мс / p95 0,06 мс |
| Базовая текстура с box-мипами | 23–29 мс на старте вместо 109 мс |
| Отрисовка одной страны | 0,01–0,14 мс (AU 239 точек — 0,14 мс) |
| Сборка тепловой карты 175 стран | 5,1 мс и только при смене метрики |
| Тесселяция 1000 маркеров | 0,98 мс + построение 0,13 мс |
| Задержка показа | `SurfaceConfig::LOW_LATENCY`, один кадр в очереди |
| Бюджет CPU-подготовки кадра | без блокирующих операций длиннее 2 мс |

Вывод: узкое место — не GPU-пасс и не текстура. Его надо искать в
планировщике кадров и в CPU-работе до `paint`.

### 2.2. Что видно по коду (на `6c36f97`)

- `GlobeCamera::project_on_sphere` (`src/render/camera.rs:505`) вызывает
  `self.view_proj(viewport.aspect_ratio())` **на каждую точку** (`:513`).
  В цикле маркеров это повторная сборка `look_at` + `perspective` + roll
  для каждой станции.
- `marker_screens` (`src/ui/globe_view.rs:943`) на каждый кадр делает
  `sphere_point` (sin/cos) для каждого маркера, затем `deform.to_world` и
  скалярную проекцию. Результат складывается в новый `Vec`.
- `show` (`src/ui/globe_view.rs:390`) затем ещё раз проходит по видимым
  маркерам, сканирует `marker.members` для `playing`/`selected` и собирает
  второй `Vec<MarkerVisual>`.
- `paint_markers` (`src/render/markers.rs:81`) делает четыре прохода по
  массиву (`playing × selected`) и считает `pulse_fraction(time)` внутри
  каждого играющего маркера.
- Типичный N: поиск — 100, жанр — 200, догрузка страниц может увеличивать
  список; реалистичный диапазон 100–500, верхняя граница не зафиксирована.
- В `src/session/search.rs:387` и `:397` список маркеров пересобирается при
  новом ответе поиска. Отдельного ревизионного счётчика маркеров нет.

### 2.3. Статус патчей

Оба патча лежат в `src-patches/` и **не влиты** в `main`. Проверка на текущем
коммите:

```bash
git apply --check src-patches/soa-batch-projection.patch   # rc=0
git apply --check src-patches/marker-batch-vectorization.patch  # rc=0
```

Патчи перекрываются (общие hunks в `camera.rs`, `markers.rs`, `mod.rs`,
`globe_view.rs`), поэтому **это не два независимых изменения**. Второй патч
включает первый и добавляет `MarkerBatchScratch` и `marker_visuals_batch`;
принимать надо один путь, а не применять оба подряд.

До внедрения в патчах нужно исправить:

| Проблема | Почему важна |
|---|---|
| `MarkerBatchScratch::with_capacity` создаётся внутри `marker_screens`/`marker_visuals_batch` на каждый кадр | Аллокации и обнуление буферов возвращаются; смысл scratch теряется |
| `playing`/`selected` — новые `Vec<bool>` на каждый кадр | Лишние аллокации в hot path |
| `marker_screens` после переключения на `marker_visuals_batch` может остаться неиспользуемой в non-test сборке | `dead_code`/`clippy -D warnings` |
| `sphere_point` в импорте `globe_view.rs` может стать неиспользуемым | То же |
| `nearest_marker` возвращает индекс исходного маркера, а `paint_markers` сравнивает его с индексом в массиве видимых | При скрытом маркере перед наведённым кольцо подсветки попадает не на тот маркер |
| unit-SoA всё ещё пересобирается каждый кадр | `sin/cos` и запись в буферы остаются в кадре |

Последний пункт — существующая ошибка, не внесённая патчем, но батч-конвейер
делает её заметнее: hit-test и отрисовка должны работать с одним и тем же
индексом.

## 3. Бюджет кадра и метрики

### 3.1. Целевые показатели

| Режим | Политика | Критерий |
|---|---|---|
| Asleep | `reduce_motion`, окно скрыто, нет эфира и анимаций | 0 запрошенных кадров до input/IPC |
| Idle-breathing | Движение включено, эфира нет | 15 fps (66 мс), не чаще |
| Auto-spin | `motion = Off` и `reduce_motion = false`: глобус крутится сам (ADR-0023) | 30 fps (33 мс); это продуктовая анимация, не «сон» |
| Soft | Hover, callout, инерция камеры, доводка зума | 16–33 мс, только пока движение не остановилось |
| Play | Эфир, spectrum, пульс маркера, кольцо | 30 fps (33 мс) |
| `reduce_motion` + эфир | Без pulse/инерции/переворотов, но визуализатор жив | 33 мс по аудио, без анимационного хвоста |
| Взаимодействие | Перетаскивание, колесо, клик | immediate + короткий хвост 16 мс до остановки |

Важно: в OrbitFM `motion = Off` **не означает покой** — при выключенной
реактивности включается авто-вращение (ADR-0023, `auto_spin` в
`src/app.rs:754`). Настоящий «сон» даёт `reduce_motion = true` (или скрытое
окно) и отсутствие эфира/кольца/callout.

Бюджет CPU-подготовки кадра остаётся из ADR-0059: **p95 < 2 мс** без
блокирующих операций. GPU-пасс — один проход по сфере 64×32; его не трогаем,
пока профиль не покажет иное.

### 3.2. Как измеряем

1. **Span'ы `tracing`** на границах:
   - `motion_update` — `MotionMixer::update` в `src/app.rs:700`;
   - `globe_show` — `globe_view::show`;
   - `markers_project` — `marker_screens` / `marker_visuals_batch`;
   - `markers_paint` — `paint_markers`;
   - `countries_paint` — `paint_country_highlights`;
   - `globe_prepare` — `GlobeRenderer::prepare` в callback;
   - `globe_callback` — весь `GlobeCallback::prepare`.
2. **Счётчик кадров** в debug/release по `ORBITFM_FRAME_STATS=1`: кольцевой
   буфер на 600 кадров, лог p50/p95/макс раз в 5 с. Без новой зависимости;
   `Instant` + фиксированный массив.
3. **Живой probe** `#[ignore] fn marker_projection_budget_probe()`:
   прогревает 100/200/500/1000 точек и печатает p50/p95 для скалярного и
   батч-прохода. Запуск только в release, как `lod_crossing_never_stalls_the_frame`.
4. **Счётчик пробуждений**: в `FrameStats` считать кадры за 10 с покоя.
   Ожидание: 0 при `reduce_motion` без эфира, ~150 при breathing,
   ~300 при Play и при auto-spin.

Все цифры «до/после» попадают в план и CHANGELOG. Без числа изменение не
принимается — правило ADR-0059 § 4.

## 4. Карта текущего кадра и инвентаризация repaint

### 4.1. Слои

| Слой | Что делается | Где |
|---|---|---|
| Планировщик | `request_repaint*` из app, UI, фоновых задач | `src/app.rs`, `src/ui/*` |
| egui | starfield, space, vignette, маркеры, callout, кольцо | `src/ui/globe_view.rs`, `src/render/markers.rs` |
| wgpu callback | `prepare`: uniform + heat + LOD; `paint`: один pass | `src/render/globe.rs` |
| CPU до GPU | `motion.update`, проекция маркеров, страны, heatmap | `src/app.rs`, `src/render/*` |
| Ресурсы | decode/mip Земли в worker | `src/render/globe.rs` |

### 4.2. Путь маркера сейчас

```text
GlobeMarker[] (lat/lon)
  → marker_screens: для каждого
      sphere_point (sin/cos)
      → deform.to_world
      → camera.project_on_sphere
          → view_proj(aspect) заново
          → back-face, clip, NDC, viewport
  → Vec<(source_index, Pos2)>
  → show: второй проход, members.iter().any(...) → Vec<MarkerVisual>
  → paint_markers: 4 прохода, circle_filled/stroke, pulse на каждый playing
```

### 4.3. Инвентаризация `request_repaint*`

Все пути на `6c36f97`; классификация — предложение для волны 1.

| Место | Сейчас | Класс | Комментарий |
|---|---|---|---|

| `app.rs:397` | immediate после poll интеграций | Background | Можно оставить, событие редкое |
| `app.rs:427` | 120 мс, пока busy favicon | Background | Опрос очереди, не анимация |
| `app.rs:1271` | 33 мс при intensity > 0,01/flip, иначе 66 мс | Play / Breathing | Дублируется с `globe_view` |
| `app.rs:1518` | immediate после любого `UiAction` | Input | Законно, но стоит проверить, не слишком ли широко |
| `app.rs:1998` | 33 мс при Playing/Buffering и visualizer | Play | Spectrum |
| `app.rs:2003` | точный дедлайн сна | Deadline | Один будильник, не трогать |
| `globe_view.rs:475` | 16 мс при затухании callout | Soft | Только пока fading |
| `globe_view.rs:480` | 33 мс при playing/ring | Play | Пульс/кольцо |
| `globe_view.rs:485` | 33 мс при idle spin | Soft | Медленное авто-вращение |

Главные наблюдения:

- Нет единой точки, где видно «кто и зачем просит кадр». Один путь может
  просить immediate, другой — `after`, и окно просыпается чаще, чем нужно.
- В Play одновременно работают `app.rs:1271`, `app.rs:1998` и

- В Idle с `reduce_motion` и без эфира источников кадров быть не должно;
  это надо закрепить тестом, а не полагаться на разбор веток. Отдельно
  проверить auto-spin: при `motion = Off` он законно держит 33 мс.

## 5. Волны работ

### Волна 0 — baseline и инструментация

**Цель:** увидеть, что именно стоит оптимизировать, и получить «до».

Задачи:

1. Добавить span'ы из § 3.2. Имена — стабильные, чтобы фильтровать
   `RUST_LOG=orbitfm=trace`.
2. Добавить `FrameStats` (фиксированный кольцевой буфер, без аллокаций в
   кадре) и вывод p50/p95 раз в 5 с при `ORBITFM_FRAME_STATS=1`.
3. Добавить `#[ignore]`-probe для 100/200/500/1000 маркеров: скалярный путь
   и будущий батч. Замер в release на i5-8300H/GTX 1050 Ti Mobile.
4. Записать baseline в этот файл (таблица «до») и в CHANGELOG при релизе.

**Критерий выхода:** есть числа p50/p95 для `motion_update`,
`markers_project`, `markers_paint`, `globe_prepare` и кадров/с при
Asleep/Breathing/Auto-spin/Play. Поведение не меняется.

### Волна 1 — политика перерисовки

**Цель:** один язык для всех видов кадров и отсутствие лишних пробуждений.

Задачи:

1. Ввести `src/ui/repaint.rs`:
   ```rust
   pub(crate) enum RepaintReason {
       Input,        // immediate
       Interaction,  // 16 мс, пока не остановилось
       Callout,      // 16 мс
       Playback,     // 33 мс
       IdleSpin,     // 33 мс
       IdleBreath,   // 66 мс
       Background,   // 110–120 мс, конкретика у вызывающего
       Deadline(Duration),
   }

   pub(crate) fn schedule(ctx: &egui::Context, reason: RepaintReason);
   ```
   Чистая функция `cadence(reason) -> Option<Duration>` тестируется без egui.
2. Перевести `app.rs` и `globe_view.rs` на helper; константы
   `SPECTRUM_REPAINT`/`MOTION_IDLE_REPAINT`/`CALLOUT_REPAINT` переезжают туда
   или остаются алиасами, чтобы не менять поведение в первый коммит.
3. Убрать дублирование Play-источников: `app.rs:1271` оставляет только
   Breathing, если `globe_view` уже держит Play/Interaction; либо оба
   используют общий `RepaintPlan`. Решение — по замеру кадров/с.
4. Зафиксировать режимы:
   - **Asleep**: `reduce_motion = true` (или окно скрыто), нет эфира, нет
     callout/ring/favicon — ни одного запроса. `motion = Off` сюда **не**
     входит: он включает авто-вращение.
   - **Breathing**: движение включено, эфира нет — 66 мс; при потере фокуса
     окна — 100 мс, если владелец согласен (см. § 8).
   - **Auto-spin**: `motion = Off`, `reduce_motion = false` — 33 мс, пока
     глобус крутится; это существующее поведение ADR-0023.
   - **Play**: 33 мс; 60 fps только на взаимодействии и коротком хвосте.
   - **Soft**: 16–33 мс, пока есть причина; после settle — ноль.
5. Проверить скрытое окно: `analysis_needed()` уже выключает анализ, но
   `request_repaint_after` из виджетов не должен будить невидимый стол.
6. Если по замеру видно, что несколько источников всё ещё дают лишние
   кадры, ввести `RepaintPlan` в `OrbitApp` (собирает `immediate` и
   минимальный `after`, применяет один раз в конце `draw`). Это второй шаг,
   не обязательный для первого.

**Критерий выхода:**

- Asleep (`reduce_motion`, без эфира) — 0 кадров за 10 с; Breathing —
  15 ± 1 fps; Auto-spin и Play — 30 ± 2 fps; взаимодействие — без пропусков.
- Тесты на `cadence`: таблица режимов, `reduce_motion` не даёт pulse,
  Deadline не превращается в периодический кадр.
- ADR-0064 «Политика перерисовки и бюджет кадра», если владелец принимает
  режимы как контракт. Иначе — раздел в `docs/modules/04-render-globe.md`.

### Волна 2 — батч-проекция маркеров

**Цель:** одна `view_proj` и один `eye` на кадр; никаких `sin/cos` и
`Option` в проекционном цикле; визуальная семантика не меняется.

**Решение по патчам:** берём `marker-batch-vectorization.patch` как основу
(он включает `SpherePointSoA`, `MarkerBatchScratch`,
`project_points_on_sphere[_soa]`, `marker_visuals_batch`). Первый патч
отдельно не применяем — это подмножество. Перед merge патч дорабатывается,
а не принимается «как есть».

Задачи:

1. Применить второй патч, затем исправить:
   - `MarkerBatchScratch` хранится в `OrbitApp` (поле) и передаётся в
     `GlobeState` как `&mut`; `with_capacity` в кадре не вызывается.
   - `playing`/`selected` — поля scratch, очищаются и переиспользуются.
   - `marker_visuals_batch` принимает `&mut MarkerBatchScratch`.
   - `marker_screens` либо удаляется, либо остаётся `#[cfg(test)]`;
     тест `marker_screens_follow_the_deformation` переводится на новый путь.
   - Лишний импорт `sphere_point` убирается, если больше не нужен.
2. Исправить индекс наведения:
   - `nearest_marker` возвращает `MarkerHit { source: usize, slot: usize }`
     (или пару), где `slot` — позиция в массиве видимых;
   - `paint_markers` получает `hovered_slot`, а подпись — `source`;
   - клик по-прежнему выбирает `state.markers[source]`;
   - тест: первый маркер за горизонтом, второй виден; наведение на второй
     подсвечивает второй, а не первый.
3. Сохранить `project_on_sphere` для одиночных вызовов (якорь карточки,
   страны, тесты). Батчевый AoS-метод `project_points_on_sphere` оставить для
   стран/будущих точек, но не подключать туда, где семантика отличается
   (`project_fill` требует «все точки видимы», а не подмножество).
4. Добавить тесты:
   - `batch_and_soa_match_scalar_projection` (из патча) — паритет с
     `project_on_sphere` по позициям и индексам;
   - пустой вход, все точки за горизонтом, несовпадающие длины SoA,
     нулевой/нечисловой viewport;
   - `out_positions`/`out_indices` очищаются даже при раннем выходе;
   - `deform_into` совпадает с `to_world` для нескольких точек.

**Критерий выхода:**

- `cargo test --lib batch_and_soa_match` и
  `cargo test --lib marker_screens_follow` зелёные (точные имена:
  `batch_and_soa_match_scalar_projection`, `marker_screens_follow_the_deformation`).
- Позиции видимых маркеров совпадают со скалярным путём в пределах `1e-4`.
- `markers_project` p95 при N=500 улучшился не менее чем на 30 % или
  укладывается в 0,3 мс; иначе оставляем только hoisting `view_proj` и
  честно фиксируем, что батч не окупился.
- Нет новых аллокаций в кадре после прогрева (проверка по capacity scratch
  и отсутствию `Vec::new` в hot path).

### Волна 3 — кэш unit-координат, флаги, мелкие hot-path правки

**Цель:** убрать из кадра то, что не меняется между кадрами.

Задачи:

1. Ввести ревизию списка маркеров:
   - поле `markers_revision: u64` в `Session` (или обёртка `MarkerSet`);
   - инкремент в `src/session/search.rs:387` и `:397` при
     `self.markers = build_markers(...)`, а также в любом будущем месте
     пересборки;
   - тест: новый ответ поиска увеличивает ревизию, повторный кадр — нет.
2. `SpherePointSoA` кэшируется в `MarkerBatchScratch`:
   ```rust
   pub fn project_lat_lons_cached(
       &mut self,
       camera: &GlobeCamera,
       viewport: Rect,
       deform: GlobeDeform,
       revision: u64,
       lat_lon: impl IntoIterator<Item = (f32, f32)>,
   )
   ```
   При совпадении ревизии `fill_lat_lons` не вызывается; каждый кадр —
   только `deform_into` + `project_points_on_sphere_soa`.
   В тестах — счётчик перестроений; после смены ревизии ровно одно.
3. Флаги `playing`/`selected` кэшировать по ключу
   `(markers_revision, current_uuid, selected_uuid)`. Сейчас `members.iter()`
   сканируется на каждый маркер каждый кадр; при плотных группах это
   заметнее проекции. Буферы — `Vec<bool>` в scratch, без аллокаций.
4. `nearest_marker` перевести на квадрат расстояния:
   `distance_sq <= MARKER_CLICK_RADIUS * MARKER_CLICK_RADIUS`; выбор — по
   `distance_sq`. Поведение то же, `sqrt` из цикла уходит.
5. `paint_markers`: `pulse_fraction(time)` считать один раз на кадр и
   передавать в `paint_marker`; четыре прохода оставить, если замер
   `markers_paint` < 0,5 мс. Если больше — собрать порядок отрисовки один раз
   в scratch (playing/selected сначала), без аллокации на кадр.
6. Проверить, что `deform_into` не пишет лишнего: world-кэш по `GlobeDeform`
   добавлять только если профиль покажет, что O(N) умножений заметны.

**Критерий выхода:**

- После прогрева кадр не аллоцирует `Vec` для маркеров; capacity стабильна.
- `markers_project` не растёт при повторных кадрах с той же ревизией;
  `sin/cos` в кадре отсутствуют (подтверждается счётчиком/профилем).
- `nearest_marker` не регрессирует по кликам; тест на границу радиуса.

### Волна 4 — GPU и egui: только по замеру

**Цель:** убрать оставшиеся мелкие траты, не трогая стек.

Задачи (каждая включается только при выходе за бюджет):

1. **Dirty uniform.** `GlobeRenderer::prepare` (`src/render/globe.rs:342`)
   всегда делает `queue.write_buffer` (`:349`). Хранить последний
   `CameraUniform` и пропускать запись, если он не изменился. Сравнение —
   побайтово или через `PartialEq` (поля `f32`; камера обязана быть
   конечной). Замер: сколько записей юниформа приходится на кадры, где
   камера/движение не менялись (toast, favicon, callout).
2. **Starfield bake.** `paint_starfield` (`src/ui/globe_view.rs:128`) рисует
   160 `circle_filled` каждый кадр. Если span показывает > 0,2 мс —
   собрать один `egui::Mesh` (или `Shape::mesh`) при первом кадре/смене
   размера области и переиспользовать. Позиции и цвета статичны; тест —
   вершины/количество не меняются между кадрами.
3. **Marker paint.** Если `markers_paint` > 1 мс на 500 маркерах — сначала
   убрать glow у неиграющих/невыбранных на дальнем зуме или собрать
   предварительную тесселяцию; LOD со скрытием станций — только по решению
   владельца (§ 8). Не начинать с LOD.
4. **Страны.** `project_fill`/`project_runs` (`src/render/countries.rs:130`,
   `:217`) остаются скалярными: ADR-0059 измерил 0,01–0,14 мс на страну,
   рисуются максимум выбранная и наведённая. Батч подключать только если
   новый span `countries_paint` даст > 0,3 мс p95.
5. **Heatmap.** `CountryHeatCache` уже кэширует по
   `(search_revision, world_revision, metric)`; сборка 5,1 мс происходит
   только при смене метрики. Если это выбьет p95 кадра — вынести в worker
   по образцу LOD-текстуры, но не в первой итерации.
6. **Шейдер/поверхность.** Не менять `globe.wgsl`, не включать MSAA/HDR,
   не пересоздавать bind group. `LOW_LATENCY` уже включён.

**Критерий выхода:** каждая правка имеет число «до/после» и не ухудшает
p95. Если выигрыш в пределах шума — правка отклоняется.

### Волна 5 — SIMD/GPU только при доказанной необходимости

**Условие входа:** после волн 2–3 `markers_project` p95 при N=500 на
i5-8300H остаётся > 0,5–1 мс, и профиль показывает именно проекционный
цикл (а не `paint`/`egui`).

Порядок:

1. Проверить авто-векторизацию LLVM: `cargo asm`/`perf` для
   `project_points_on_sphere_soa`; убедиться, что цикл не разваливается из-за
   ветвлений.
2. Локально попробовать `-C target-cpu=native` **только для замера**; в
   релизные артефакты не включать (совместимость важнее).
3. Если нужно — обсудить `wide`/`std::simd` как отдельное решение с ADR:
   маски вместо `if` на точку, 4/8 lane, выравнивание. Это новая зависимость
   или nightly-функция, поэтому без одобрения владельца не начинать.
4. GPU-проекция маркеров — только если N стабильно > 5k и маркеры уже
   переносятся в wgpu-пасс. Для 100–500 станций это лишний sync.

**Критерий выхода:** либо есть ускорение ≥ 2× на изолированном probe без
регрессии точности, либо волна закрывается как «не требуется».

## 8. Риски и открытые вопросы

| Риск / вопрос | Влияние | Решение |
|---|---|---|
| Idle-breathing 15 fps конфликтует с «Idle 0 FPS» из материалов | Нельзя молча убрать продуктовую анимацию ADR-0028 | Оставить 15 fps по умолчанию; 0 fps — только при `reduce_motion`/скрытом окне; `motion = Off` — это auto-spin 30 fps (ADR-0023); снижение breathing до 10 fps или пауза при потере фокуса — решение владельца |
| LOD маркеров скрывает станции | Меняет UX и семантику ADR-0012 | Не делать в этом плане; отдельное решение с критериями (зум, приоритет по votes, подпись) |
| Кэш ревизии не покрывает все пути пересборки маркеров | Устаревшие координаты | Централизовать `build_markers` в одном методе `Session`; тест на каждый путь; `debug_assert` ревизии |
| `GlobeDeform` меняется каждый кадр | World-кэш может быть бесполезен | Кэшировать только unit; world считать каждый кадр, пока профиль не докажет обратное |
| Патчи не проходят clippy из-за мёртвого кода/импортов | CI красный | Исправить до merge; прогнать оба clippy-профиля |
| Ошибка индекса наведения существовала до патча | Может изменить поведение | Считать исправлением, добавить тест; отметить в CHANGELOG |
| Замеры шумят на ноутбуке | Ложные выводы | p50/p95, несколько прогонов, release, фиксированное окно 1100×800 |
| `u32` для индексов | Теоретическое переполнение | `debug_assert!(markers.len() <= u32::MAX as usize)`; на практике N < 10k |
| Перенос scratch в `OrbitApp` усложняет `GlobeState` | Больше связности | Альтернатива — `RefCell`/`thread_local`; предпочтителен явный `&mut`, как у callout |

1. Оставляем ли idle-breathing 15 fps на батарее или снижаем при потере

2. Нужен ли LOD маркеров как визуальная функция (не только производительность)?
3. Допустима ли новая зависимость (`wide`) ради SIMD, если профиль докажет

## 9. Чего сознательно не делаем

- Не переписываем рендер на `ash`/`vulkano` и не меняем `eframe`/`wgpu`.
- Не включаем continuous rendering и не «крутим шар» ради плавности.
- Не оптимизируем WGSL, пока не убраны лишние кадры.
- Не переносим маркеры в GPU-пасс и не делаем compute-radii для 100–500

- Не меняем визуальный дизайн маркеров, стран, звезд и кольца.

### Волна 0 — baseline и инструментация (2026-11-12)

Реализовано, поведение кадра не менялось:

- `#[ignore] fn marker_projection_budget_probe()` в `src/ui/globe_view.rs`


#### Вывод по волнам 2 и 3

`markers_project` при N=500 — **p95 0,034 мс**, это в 8 раз ниже бюджета 0,3 мс
из критерия волны 2. Почти вся цена — повторная сборка `view_proj` на точку
(колонка справа совпадает со `markers_project`), но в абсолютных числах это
десятки микросекунд, невидимые на фоне бюджета CPU-подготовки 2 мс (ADR-0059 § 4).

Решение по правилу «без числа изменение не принимается»:

- **Волна 2 в объёме патча не окупается.** `SpherePointSoA`,
  `MarkerBatchScratch`, SoA-цикл и кэш добавляют сложность ради ≤ 0,03 мс.
  Оставляем только hoisting `view_proj` (одна матрица на кадр) как чистку и
  **обязательно** переносим из волны 2 исправление индекса наведения — это
  корректность, а не производительность.
- **Волна 3 (кэш unit-координат и флагов) тоже не окупается:** `sin/cos` и
  `deform` на 500 точках уже уложены в те же 0,026 мс p50, что и один `view_proj`
  на точку.
- Фокус бюджета — планировщик кадров (волна 1); `markers_paint` (тесселяция
  egui) требует отдельного замера, но по ADR-0059 1000 маркеров ≈ 0,98 мс, то
  есть N=500 укладывается в бюджет волны 4.

#### Ещё не собрано

Живые fps по режимам (Asleep / Breathing / Auto-spin / Play) — `frame_tick`
пишет их при `ORBITFM_FRAME_STATS=1`, но нужен ручной прогон на столе владельца;
числа добавить сюда и в CHANGELOG при релизе.

### Волна 4 — первый замер: отрисовка маркеров (2026-11-12)

Добавлена вторая проба — `#[ignore] fn marker_paint_budget_probe()` в
`src/render/markers.rs`: строит `MarkerVisual` и отдельно меряет painting
(`begin_pass` → `paint_markers` → `end_pass`) и тесселяцию egui.

```bash
cargo test --release marker_paint_budget -- --ignored --nocapture
```

| Нарисованных маркеров | paint p50 / p95, мс | tessellate p50 / p95, мс |
|---|---|---|
| 100 | 0,018 / 0,039 | 0,064 / 0,128 |
| 200 | 0,037 / 0,063 | 0,427 / 0,595 |
| 500 | 0,101 / 0,211 | 1,400 / 2,283 |
| 1000 | 0,245 / 0,721 | 2,302 / 4,482 |

**Вывод:** настоящая цена маркеров — не проекция и не построение форм
(paint ≤ 0,2 мс), а **тесселяция egui**: 500 нарисованных маркеров ≈ 2,3 мс p95,
1000 ≈ 4,5 мс. Это выше порога волны 4.3 (1 мс на 500).

Важные оговорки:

- Считаются **нарисованные** маркеры, а не длина списка: при списке N=500
  видимых ≈ 194 (замер § 11), то есть реальная цена ≈ 0,6 мс p95 — под порогом.
  Риск появляется на списках 1000+ (типично для страны/жанра с догрузкой
  страниц).
- Метрика `markers_paint` из `frame_stats` меряет только построение форм
  (≤ 0,2 мс), но **не** тесселяцию: та живёт в eframe после кадра и в app-уровневые
  границы не попадает. Ориентироваться на `markers_paint` как на «цену маркеров»
  нельзя — правду даёт только этот probe.
- В пробе у каждого маркера включено гало (1 круг) + ядро + контур; каждый
  20-й играет (пульс-кольцо + гало), каждый 50-й выбран. Это соответствует
  плотной выборке, но не худшему случаю (все playing/selected).

**Решение по волне 4.3:** правку не начинать, пока список станций не станет
стабильно 1000+. Первый шаг тогда — не LOD (это UX-решение владельца, § 8), а
сокращение числа форм: убрать внешнее гало у неиграющих/невыбранных на дальнем
зуме или собрать статику звёзд/маркеров в `egui::Mesh`. Оценка выигрыша —
повторный прогон этой пробы.
